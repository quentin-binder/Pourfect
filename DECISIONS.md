# Decisions

Short entries, newest at the bottom.

1. **Repo layout.** The repo root is `LiquidPour/` (not `BottleSort/`). The existing Xcode project `LiquidPour.xcodeproj` and its folder `LiquidPour/` play the role of the spec's `App/`. `Packages/BottleSortCore` and `Levels/` sit at the repo root as specified.
2. **No XcodeGen.** XcodeGen isn't installed and the user already created the Xcode project, so we keep it and make small targeted edits to `project.pbxproj` (user-approved) instead of generating one.
3. **Platforms.** App target supports iOS/iPadOS and native macOS (arm64 + x86_64 universal, via SwiftUI multiplatform — not Catalyst, not "Designed for iPad"). visionOS removed. Minimum iOS 17 / macOS 14 (matches the package platforms and `@Observable`).
4. **Git.** Commits go directly on `main` (user choice). Per-user Xcode state (`xcuserdata`) is ignored.
5. **Tooling.** Package uses swift-tools-version 6.0 (Swift 6 language mode, strict concurrency; all model types are `Sendable` value types). Tests use Swift Testing (`import Testing`), which ships with the toolchain — no third-party deps.
6. **Rules in one place.** `Rules.pourAmount(from:to:)` is the single legality + amount check (returns 0 = illegal); `Rules.movableRunCount` and `Rules.isSolved` are the other hooks. `GameState.canPour/pouring/legalMoves/isSolved` all delegate to it. Locked bottles are already rejected there (cheap, and the field exists now).
7. **Move counter.** `GameSession.moveCount` = number of moves currently applied, so Undo decreases it. Stars compare this with `minMoves`.
8. **Validation scope.** `validate()` checks: at least one bottle, capacity ≥ 1 and identical across bottles, no overfilled bottle, every color exactly `capacity` times. It does not check solvability (that's the solver's job).
9. **Per-user Xcode files untracked.** `xcuserdata/` removed from the index (files stay on disk) — user-approved.
10. **macOS input.** A click acts as a tap. Haptics only on iOS; the illegal-move shake animation runs on both platforms — user-approved.
11. **State encoding.** `StateKey` packs each bottle into a `UInt64` (6 bits per layer, ≤ 9 layers; lock id in the top byte) and sorts the codes → order-independent, includes `lockedBy`. Limits: capacity ≤ 9, color ids 0…61. Out-of-range states return `.unknown(.unsupportedState)`.
12. **Rules stay single-sourced in the solver.** The BFS generates moves through `Rules.pourAmount` / `GameState.pouring`; it doesn't re-implement pours on the packed form. Search tree stores only `(parent, move)` per node; paths are replayed from the start state, so canonical reordering never corrupts move indices.
13. **Pruning (all in `Solver.candidateMoves`).** (1) skip sources that are full + single-color; (2) skip pouring into an empty bottle when the whole source moves (canonical no-op); (3) only the first empty bottle is tried as an empty target. All three only remove moves whose result is canonically identical to the current state or to a sibling. Verified: solver optimum == naive unpruned BFS on 125 random small puzzles (test `matchesReferenceAndReplays`).
14. **Performance.** BFS was fast enough without A*: 8 colors / cap 4 / 2 empty solve in 9–42 ms in release (12 seeds, 4k–19k states). Debug-build test bound is 10 s.
15. **Hint API.** `Solver.hint(for:)` returns `HintResult` (`.move`, `.alreadySolved`, `.unsolvable`, `.unknown`) instead of `Move?`, so the UI can show "No solution from here — undo?".
16. **Dead-end ratio.** Exact when the whole reachable graph (with the same safe pruning) has ≤ 400k states: full BFS → reverse edges → mark states that can reach a win; ratio = unsolvable / all. Otherwise: 48 seeded random walks (length 1…2×minMoves) whose endpoints are solved with a 200k-state cap; ratio over decided samples (`deadEndMethod = .sampled`). Every starter-pack level was exact.
17. **Branching factor** = mean count of *all* legal moves (player's view, no pruning) over the states on the optimal path, excluding the final state.
18. **Score formula** (tunable): `minMoves + 1.5·log2(statesExplored) + 40·deadEndRatio + 0.5·branchingFactor`, rounded to 0.1. Dead-end weight raised 15 → 40 (user choice) so trap-heavy 1-empty levels rank as hard as they play.
19. **Generator seeds.** Attempt i of a config uses `seed + i`; a level's `meta.seed` alone (+ colors/capacity/empty) reproduces it. Own Fisher–Yates on SplitMix64 (stdlib `shuffle(using:)` isn't guaranteed stable across Swift versions). The min-moves filter runs before the full difficulty report (cheaper).
20. **Starter pack** (`levelgen --preset starter`): tiers 3c/cap3 ×2, 3c ×3, 4c ×7, 5c ×8, 6c ×6, 5c/1-empty ×2, 7c ×5, 6c/1-empty ×2, 8c ×5 (all cap 4 unless noted). Each tier has its own seed space (`seed + tier × 1e6`); the final pack is sorted globally by score (user choice), so color counts can interleave. Move ranges were tuned from measured distributions.
21. **JSON output.** Keys sorted, pretty-printed, layer arrays collapsed to one line for hand-curation. Extra meta fields (`statesExplored`, `deadEndRatio`, `branchingFactor`) are informational. Loader rejects unknown versions and duplicate ids, and validates every level.
22. **levelgen language mode.** The CLI target compiles in Swift 5 mode (a plain top-level script); the core library stays in Swift 6 strict mode.
23. **Project wiring.** `project.pbxproj` gained an `XCLocalSwiftPackageReference` to `Packages/BottleSortCore`, the `BottleSortCore` product dependency, and a `Levels` group whose `pack_01.json` is in the Resources phase (the app folder itself is a synchronized group, so new Swift files need no project edits).
24. **App architecture.** `LevelCatalog` (bundled pack), `ProgressModel` over a `ProgressStore` protocol (`UserDefaultsProgressStore`, key `progress.bestStars.v1`; a level unlocks when the previous one has ≥ 1 star), `GameViewModel` (`@Observable`, main actor) wrapping `GameSession`. Views hold no rules. Star thresholds live in core (`StarRating`).
25. **Background solving.** After every move the view model solves the new state in a detached task (1M states / 4 s cap). The result detects "stuck" (unsolvable) and is cached so Hint is instant; Hint falls back to a fresh background solve. Results for stale states are discarded.
26. **Stuck rule.** "Stuck — undo or restart?" shows when there are no legal moves, or the solver proves the position unsolvable. The player may keep moving while it's shown.
27. **Animation.** Pours animate with SwiftUI transitions (layers fade out of the source and slide in at the target), the selected bottle lifts, illegal moves shake (GeometryEffect) and fire `.sensoryFeedback(.impact)` (haptic on iPhone; no-op on most Macs). Win fires `.success`.
28. **Keyboard (Mac/iPad).** ⌘Z Undo, ⌘R Restart, ⇧⌘H Hint, Return = Next on the win card.
29. **Debug launch arguments** (DEBUG builds only): `-LPOpenLevel N` opens level N directly (ignores locks); `-LPDemoMoves K` plays the first K optimal moves through the normal tap path. Used for automated screenshots.
30. **One pour function.** `Rules.pour(from:to:) -> (source, target)?` computes the resulting bottles for every move kind (color run, or key → consume + unlock); `GameState.canPour/pouring/legalMoves` and the solver delegate to it. `Rules.pourAmount` remains as a derived helper (layers leaving the source; 1 for a key). Supersedes the "single legality check" part of #6.
31. **Key & lock rules** (Phase 5, spec wording): a key moves only when on top, always alone (`movableRunCount == 1`), and only into the bottle with `lockedBy == key`; that bottle unlocks and the key disappears (needs no free slot — a full locked bottle can be opened). Colors never go onto a key or into a locked bottle; locked bottles can't be poured from. A locked bottle or one containing a key is never "solved", so a win implies no keys and no locks.
32. **Key JSON / encoding.** Key layer = `{"key": n}`, bottle lock = `"lockedBy": n`; layer lists with keys are still collapsed onto one line. `StateKey` tokens: 0 empty, 1…47 colors 0…46, 48…63 keys 0…15 (lock byte = lockedBy + 1, limited to 0…15 too). Supersedes the limits in #11.
33. **Key validation.** Colors still exactly `capacity` each (keys don't count); each key id at most once as a layer (`duplicateKey`), at most one bottle per lock id (`duplicateLock`), and every lock has a key and vice versa (`lockWithoutKey`, `keyWithoutLock`). A key nested inside another locked bottle is allowed.
34. **Pruning with keys.** Rule 3 now only skips *unlocked* empty targets (a locked empty bottle is a key target, not interchangeable). Rule 2 likewise only applies to unlocked empty targets; a lone key "moves whole" but can't go into an unlocked bottle anyway. Rule 1 can't hit key bottles (`isSolved` is false). Verified against the naive BFS on 175 random lock levels (`matchesReferenceOnLockLevels`) plus a hand-made puzzle that needs the key (4 moves; wrong-key and buried-key variants are unsolvable).
35. **Lock generator** (`GeneratorConfig.locks`, `levelgen --locks N`, 0 ≤ N < colors). Same shuffled color layers as classic; then: (1) the first `N × capacity` layers fill N *full* locked bottles (keys 1…N); (2) the remaining `(colors − N) × capacity` colors plus the N keys are dealt in sequence into unlocked bottles of `capacity` layers, the last one partial — one bottle more than classic, its free space is where the keys "came from"; (3) a slot is "top" if it is the last of its bottle; the non-top slots are shuffled and the first N (in sequence order) become keys 1…N, colors fill the rest in shuffled order; (4) empties are appended. With `locks = 0` the RNG use and output are identical to before, so `pack_01.json` is unchanged. The "pre-solved bottle" rejection also covers a locked bottle that would be solved once opened.
36. **Hidden layers** (display only, solver ignores them). `LevelDefinition.hidden: Bool?` (JSON `"hidden"`, omitted when false). `GameSession(_:hidden:)` keeps a per-bottle `hiddenDepth` = bottom layers shown as "?": starts at `count − movableRunCount`, after each move `min(old, count − movableRunCount)`; stored with the undo history, so undo/restart restore it exactly. Query with `isHidden(bottle:layer:)`. (With the current rules the new value is never larger anyway, but the `min` makes permanence explicit.)
37. **Random levels.** `RandomLevel.generate(options, seed:, maxAttempts: 6, limits:, progress:)`: attempt i uses generator seed `seed + i`, no difficulty filter; rejected if a bottle is pre-sorted, or the solver says unsolvable/unknown. Default limits 1M states / 4 s per attempt. Result has the level (`id "random-<seed>"`, `hidden` in `.hidden` mode, meta seed = the attempt's seed) or nil after the cap, plus every attempt's outcome. Options clamp to colors 2…12, capacity 2…6, empty 0…4, locks 1…2 (and < colors; only used in `.locksAndKeys`). `progress(k, max)` fires before attempt k.
38. **Quick difficulty budget.** Random levels are scored with `DifficultyBudget.quick` (exact dead-end graph ≤ 50k states, else 12 samples × 20k states) so the button stays responsive (≤ ~2.5 s release on an M-series Mac for 12 colors/cap 6 or 10 colors + 2 locks). `levelgen` and the pack keep `DifficultyBudget.default` (unchanged numbers).
39. **Pour animation** (replaces the pour part of #27). Pure SwiftUI on both platforms. The view model applies the move first, then publishes a `PourEvent` (from, to, moved layer, amount, both bottles before the move, their hidden depths). The view only draws it and reports back with `finishPour(id)`. Taps during a pour are queued (up to 2) and replayed. Undo, restart and level changes cancel the pour with no animation. Win and stuck cards wait until the pour ends. A 3 s failsafe in the model ends a pour if the view never reports back.
40. **Bottle positions for the animation.** Each bottle reports its frame through an `Anchor<CGRect>` preference. A board overlay draws the source, the stream and the target while the two real bottles are hidden; the overlay re-reads the frames every frame.
41. **Driving the animation.** A `TimelineView` evaluates a pure `PourPose.at(t)` (1.1 s total) instead of chained `withAnimation` calls — easy to read and tune, and it can't drift.
42. **Liquid in a tilted bottle.** Drawn in the bottle's own space with the surface kept level: each layer keeps its area, and its boundaries are found by bisection on the bottle's rectangle (rounded corners ignored). The tilt angle is where the remaining liquid reaches the lip, kept between 55° and 86°. Surface sway is a small damped extra tilt. **Reduce Motion:** level change in place over 0.4 s, no flight, tilt or stream.
43. **Key & lock look.** Key/lock colors are a separate metallic list in `Palette` (`keyColors`, by `KeyID`), so they never read as a liquid. A key layer is a dark slot with a `key.fill` icon in its color; a locked bottle gets a `lock.fill` badge in the same color, dimmed contents and a tinted outline. The views only read `Layer` / `Bottle.lockedBy`; no rule is evaluated in the app.
44. **Key pour animation.** Same flight and tilt as a liquid pour, but no stream: the key leaves the source in one piece, falls (rotating, shrinking) into the lock at the target's center, then the lock scales up and fades (`unlock` = last quarter of the flow). The target gains no layer.
45. **Hidden layers in the app.** `BottleView` takes `hiddenLayers` = `GameSession.hiddenDepths[i]`; those bottom layers show as a grey "?" card. A reveal is a 3D flip (0.45 s, face swapped at 90°). While a pour animates, the source keeps its pre-move depth so the flip plays when the board bottle reappears. In the flying overlay the tilted Canvas draws the same glyphs at each band's center ("?" on hidden layers, the key icon on key layers), tilting with the bottle.
46. **Random levels in the app.** `RandomLevelMaker` (main-actor, observable) runs `RandomLevel.generate` in a detached task with a seed from the system RNG (1…999 999 999, so ids stay readable); the core stays deterministic for a seed. Progress hops back to the main actor; a generation counter drops stale results, and `cancel()` also cancels the task, which stops the core run (see #48). Settings are stored as plain `UserDefaults` keys (`random.mode`, `random.colors`, …) and clamped with `RandomLevelOptions.clamped`. Navigation uses a `Route` enum (`level`, `randomSettings`, `random(level, options)`). A random game gets `GameViewModel(randomLevel:options:)`: no `ProgressModel` (never recorded), title "Random · <mode>", and "New Random Level" on the win card regenerates with the same options in place.
47. **More DEBUG launch arguments** (extends #29): `-LPRandomSettings 1`, `-LPRandomGenerate 1`, `-LPRandomMode classic|locks|hidden`, `-LPRandomSeed S`; the saved settings can be overridden per run through the UserDefaults argument domain (`-random.colors 6`).
48. **Random levels are deterministic; cancellation is real** (amends #37 and #46). `RandomLevel.defaultLimits` is now 1M states with *no* timeout, so a seed gives the same level (or none) on every device; a wall-clock limit made the accept/`unknown` decision depend on device speed. Worst case is about 5 s per attempt (release, M-series Mac). Long runs are stopped by cancelling the task instead: the solver checks `Task.isCancelled` every 4096 states (`.unknown(.cancelled)`), and `generate` makes no further attempts once cancelled. The in-game analysis keeps its 4 s timeout (its result is never stored).
49. **Stricter validation** (extends #8 and #33). `validate()` also rejects what the solver can never handle — capacity above `StateKey.maxCapacity` (9, `invalidCapacity`), color ids above 46 (`colorOutOfRange`), key/lock ids outside 0…15 (`keyOutOfRange`) — and locks that can never open (`unopenableLock`): a key inside the bottle it unlocks, or behind a cycle of locks. A key nested in another locked bottle whose key *is* reachable is still allowed.
50. **Stale background work is cancelled** (app side of #48). The view model forwards cancellation into its detached solves (`withTaskCancellationHandler`), so a superseded per-move analysis or hint stops within 4096 states. Replay/Restart and Undo cancel a pending "New Random Level" (the finished level no longer replaces a board the player went back to), and so does leaving the game screen.
51. **Spec removed.** `BOTTLE_SORT_PROTOTYPE_SPEC.md` was deleted from the repo at the user's request; earlier entries still say "the spec" for the original requirements, which stay in git history.
52. **Multiple packs.** The JSON format gains optional `name` and `subtitle`. The app bundles every `Levels/pack_*.json` (the `Levels` group is now a synchronized folder, so adding a file needs no project edit) and lists them in file order. All packs are open; levels unlock in order inside each pack. The last viewed pack is remembered with `@AppStorage` (a per-device convenience).
53. **Harder packs by selection.** A `Tier` can set `pool = k`: generate `count × k` passing levels and keep the `count` with the highest score. Combined with higher color counts, size-5 bottles, locks, hidden layers and one-empty-bottle tiers, this lifts the average score from 35.7 (Starter) to 56.5 (Challenger), 68.6 (Expert) and 71.9 (Master, max 96.3). Locks & Keys (51.1) and Hidden Depths (46.4) are themed mid-difficulty packs; the score doesn't measure hidden information. Measured limits: one empty bottle makes 6+ colors at size 4 unsolvable in 20/20 samples, so one-empty tiers use 5 colors, or 6 colors at size 5.
54. **Presets.** `levelgen --preset starter|challenger|expert|locks|hidden|master|all`. Each preset has its own base seed (1, 2000, …, 6000) and id prefix (`p1`…`p6`), so ids are unique across packs and regeneration is reproducible. `starter` reproduces the original `pack_01` levels exactly.
55. **Shipped-pack test budget.** `swift test` (debug build) solves only levels whose recorded search was ≤ 8 000 states (81 of 180), keeping the suite at ~20 s; every level is re-solved against its `minMoves` by `levelgen --report` in release.

56. **Roadmap direction (user choices).** Product name **Pourfect** with the full Potion Lab theme; code and module names stay neutral. Main path = star-gated chapters, one new mechanic each (MECHANICS.md §3); the current hard packs become an optional Challenges area.
57. **Roadmap order.** Polish → theme & chapters → daily puzzle → mechanics architecture → mechanics (C1, C2+C4, D1, D2, F1+F2, E1, A3) → challenge modes → orders & story → release. Not planned: A2 corks, B2 scrying glass, C3 cauldron capacity, C5 density, D3 conveyor, D4 evaporation, E2/E3, F3 teleports, items.
58. **Assets are generated in code.** Sounds are synthesized with AVAudioEngine; art is SwiftUI shapes, gradients and Canvas particles. Real asset files can replace them later behind the same hooks.
59. **No Game Center, iCloud or notifications.** The user has a developer account but doesn't want them; the daily puzzle works fully offline. TestFlight may come later.
60. **English only**, but all UI text goes through a String catalog so languages can be added cheaply.
61. **Design docs are tracked.** `FUTURE_FEATURES.md` and `MECHANICS.md` are committed (they still mention the removed prototype spec by name).
62. **Daily seed = UTC calendar date** so every player gets the same puzzle on the same day regardless of time zone (user-confirmed).
63. **Chapter gate:** a chapter unlocks when the previous chapter has at least half of its possible stars (user-confirmed).
64. **Hints in murky levels** stay unlimited on the main path (user-confirmed).
65. **Mixing-cauldron levels** are built backwards from a solved board, then verified by the solver (user-confirmed exception to "no backward scrambling").
66. **Bundle id `dev.qbi.pourfect`** (from the user's domain qbi.dev), applied now. Saved progress from the old placeholder id doesn't carry over.
67. **Assets:** sounds, vector art, runes and the app icon are generated in code/SVG; raster art (painted backgrounds, portraits) is listed for the user to supply later as an upgrade.
68. **Roadmap workflow:** each R-step ends with a Mac-app test checklist for the user; it's pushed to GitHub only after the user's OK.
69. **Flask completion lives in the core.** `Rules.isCompleted` = solved and not empty; `Rules.completedBottles(before:after:)` lists bottles that newly became complete. The view model computes it when the move is applied, keeps it in the `PourEvent`, and reports it when the animation lands (`finishPour`), so the cork/sound/haptic line up with the visuals. Undo/restart drop it with the pour.
70. **Feedback events.** `GameViewModel.feedback` is a short ordered log of `Feedback(id, event)` (`select`, `illegal`, `pour`, `flaskCompleted`, `levelWon`) rather than a single "last event", so events published in one update (a landing pour followed by a queued tap) are never coalesced away. Views observe `feedback.last?.id` and read `feedback(after:)`. Per-bottle `completions` counters (like `shakes`) drive visuals.
71. **Settings value and store in the core.** `GameSettings`, `ReduceMotionPreference` and `SettingsStore` / `UserDefaultsSettingsStore` are Foundation-only and live in BottleSortCore so persistence is covered by `swift test` (the app has no test target). The observable `AppSettings` wrapper and the environment values (`colorRunesEnabled`, `effectiveReduceMotion`) are in the app. Each setting is its own key, so one bad value falls back alone.
72. **Sound design.** All sounds are synthesized once at launch (deterministic seeds) into mono 44.1 kHz buffers, peaks 0.13–0.24 so they stay soft. Eight player nodes round-robin with `.interrupts`. The engine starts lazily, is rebuilt/restarted on the next sound after a configuration change or interruption, backs off 2 s after a failed start, and never starts without an output device. iOS session `.ambient` + mix with others.
73. **Haptics are imperative** (`UIImpactFeedbackGenerator` / `UINotificationFeedbackGenerator`) rather than `.sensoryFeedback`, because they are driven by the event log and gated by the haptics setting. The Mac has none, so the Haptics toggle is hidden there.
74. **Cork follows the state, the drop follows the event.** A cork is drawn whenever `Rules.isCompleted(bottle)` holds, so undo/redo/restart are always right; it pops off (removal transition) when the flask stops being complete. The drop-with-bounce and the sparkle burst (16 deterministic sparkles in the potion's color, 0.6 s, Canvas + TimelineView) play when `completions[i]` changes, i.e. when the pour lands with the cork-pop sound. A completed source that is poured from loses its cork at the start of the pour animation (`PourPose.corkOff`). With reduce motion: no drop, no bounce, no sparkles.
75. **Glass look is shared.** `GlassSheen` (soft left sheen + faint right line, over the liquid) and `potionGlow` (a blurred, faded copy of the liquid behind it, so each layer glows in its own color without tinting it) are applied identically in `BottleView` and the pour animation (`FlaskDecor.swift`).
76. **Runes.** `Rune` (Model/Runes.swift) is the single definition: 12 stroke paths indexed by color id (triangle, wave, star, chevron, crescent, bolt, diamond, heart, square, cross, hexagon, ring), drawn white over a thin dark outline at half a layer's height. One rune per layer, also inside merged runs; never on "?" or key layers. In `TiltedLiquid` runes don't affect band merging: they are drawn per original segment after the bands, tilt with the bottle and shrink with a draining/filling layer. `UserDefaultsSettingsStore` also reads string booleans, so `-settings.colorRunes 1` works as a launch argument.
77. **Cork drop runs outside the pour's animation.** The pour lands inside `withAnimation`, and that animation also eased the jump to the first keyframe: the cork started at its seat, and the leftover of that eased jump pushed it about half a flask width into the liquid while the keyframes were already back at rest (measured from screen captures; the keyframe values themselves never go below the seat, and a `.transaction` modifier on the animator did not stop it). `BottleView` now drives the animator from its own `corkDrops` counter, bumped in a transaction with animations disabled when `completions` changes. The keyframes are eased linear segments (a cubic spline through the seat dips a little below it).
78. **Reduce Motion never replays a drop.** `corkDrops` only follows `completions` while motion is on, so switching Reduce Motion in Settings doesn't change the animator's trigger (before, the trigger flipped between 0 and `completions` and every cork dropped again).
79. **Sounds are synthesized off the main actor.** `SoundSynthesis` (nonisolated) builds all samples in a detached task when `SoundEngine.shared` is first touched (now at app launch); the main actor only copies them into `AVAudioPCMBuffer`s. In the unoptimized Debug build synthesis takes ~0.75 s, which used to block opening the first level. Sounds requested before it finishes are skipped; the output is byte-identical to before.
80. **Delayed feedback is cancellable.** `SoundEngine` keeps its delayed sounds as tasks and `FeedbackPlayer` its delayed haptics; `FeedbackPlayer.cancelPending()` drops them. It runs when a pour is cancelled mid-animation (`GameViewModel.cancelledPours` goes up in Undo / Restart / level load), when the game screen disappears, and when Sound is switched off (`stopAll()` also cancels). Sound already playing is left to finish.
81. **Pourfect name, neutral code.** `INFOPLIST_KEY_CFBundleDisplayName = Pourfect` (home screen, Finder) and `InfoPlist.xcstrings` localizes `CFBundleName` to Pourfect, so the Mac menu bar (About/Hide/Quit Pourfect) and LaunchServices show the new name while `PRODUCT_NAME`, the target, the module and the executable stay `LiquidPour`. `WindowGroup("Pourfect")` and the level list's navigation title use it too.
82. **Wording.** Flasks, recipes, chapters; Random Level → **Random Brew** (modes Classic / Rune Seals / Murky Layers, "Brew" button, "New Random Brew", "Next Recipe", win card "Brewed!"). Pack names and subtitles still come from the level JSON and are not localized (they are data).
83. **String catalog.** `Localizable.xcstrings` (English, source language) holds every UI string; non-`Text` strings use `String(localized:)`. Counts with plural forms (stars, moves, flasks, murky layers, tries) use catalog plural variations/substitutions. The catalog was generated from the build's `.stringsdata` (what Xcode's IDE does on build), so it matches the code exactly.
84. **Workbench background.** `WorkbenchBackground` aspect-fills the painted workbench (landscape art when width ≥ 0.9 × height, else portrait), with a 1.5 pt blur, a 28 % black dim, a darker band across the middle and a vignette. The game screen runs in a dark color scheme (`.environment(\.colorScheme, .dark)`, and a dark navigation bar on iOS) so the glass outlines (`Color.primary`) and materials stay light on the dark scene; HUD and controls sit on ultra-thin material capsules, the result card on thick material. The level list uses `.menu`: heavily blurred art washed with the system background at 78 %, so it works in light and dark mode.
85. **Glass on a painted background.** Resting flasks get a smoky backing (`BottleView.glassBacking`, black 30 %) so empty glass reads on the art. The pour animation used an opaque `.background` fill behind the flying flask (to hide flasks it passes); on the painting that showed as a solid slab, so the target now uses the same smoky backing as at rest and the lifted source fades to a frosted `regularMaterial` backing as it rises (`opaque = min(1, rise × 1.6)`).
86. **Flask rim.** A thin glass lip (`FlaskRim`, 1.1 × the flask width, ~0.1 w tall) is drawn over the top edge in both `BottleView` and the pour animation. It's decoration only: the bottle shape, liquid clipping, tilt maths and cork position are unchanged, so fills stay pixel-identical. The rim follows the outline color (selection, hint, seal).
87. **Potion names** live next to `Palette.colors` (`potionNames`, same index) and are used for VoiceOver (`Layer.spokenName`, `Bottle.spokenContents(hiddenLayers:)`); hidden layers are spoken only as a count of murky layers, so VoiceOver never leaks them.
88. **Pack metadata.** `LevelPack` gains optional `kind` (`chapter` | `challenge`), `chapter` (1-based), `location` and `introduces: [Mechanic]`; v1 files without them still load (format version stays 1). `Mechanic` is a string wrapper (`basic`, `sealed`, `murky`, …) so files naming mechanics this build doesn't know still load. A `kind: chapter` pack without a chapter number ≥ 1 is rejected (`missingChapterNumber`). `name` stays the display name (for chapters it equals `location`); the app decides the "Chapter N · …" wording.
89. **Chapter gate in the core.** `ChapterGate.isChapterUnlocked(n, previous:)` = `n == 1 || stars × 2 ≥ maxStars` (maxStars = 3 × recipes, exactly half counts, an empty previous chapter doesn't block). `unlockedChapters(_:)` applies it in order and also needs every earlier chapter open, so stars left in a chapter that is closed again can't skip ahead. `ChapterProgress.starsToOpenNext` = ⌈max/2⌉ − stars for the UI. Recipes inside a chapter: the first is open, each further one when the previous is cleared (`isRecipeUnlocked`). Saved stars are clamped to 0…3. `ChapterOutline.plan` lists all ten planned chapters (location + mechanics) so the app can draw "coming soon" entries.
90. **New file set.** `Levels/` now holds `chapter_01.json` (= old `pack_01`, ids `p1_…`), `chapter_02.json` (Rune Vault, `c2_…`), `chapter_03.json` (Misty Marsh, `c3_…`) and `challenge_challenger|expert|master.json` (= `pack_02/03/06`, ids unchanged). `pack_04` (Locks & Keys) and `pack_05` (Hidden Depths) are deleted; their `p4_`/`p5_` ids are not reused. The renamed files were moved with `git mv`; regenerating them only added metadata (levels are byte-identical). The app's `LevelCatalog` still filters `pack_*` and has to switch to the new names.
91. **Locks must matter.** Winning always needs every key, so "the key is used" is trivially true. `LockImpact.lockMatters` instead compares with the same level without that lock (flask unlocked from the start, key layer removed): the lock matters if that level is unsolvable or the locked level needs more than one extra move (the key pour). Each lock is checked on its own; an undecided solve counts as "doesn't matter". `GeneratorConfig.requireLocksMatter` (default off, so older presets reproduce) applies it after the minMoves filter; `levelgen --report` counts a chapter lock that doesn't matter as a problem. A key lying on top of a flask that just needs emptying fails the check, which is why the chapter 2 tutorial is generated (key under a short run) rather than hand-made.
92. **Chapter presets.** Tiers can set a score window (overrides `--min/max-score`), `locksMatter`, `keepEasiest` (tutorial: easiest of a small pool) and a `section`; a pack is sorted by score inside each section and sections follow each other. Chapter 2 (seed 7000): tutorial (3 colors, size 3, 1 seal, 6 moves), then one seal with 3→6 colors and one-empty levels, then 8 recipes with two seals. Chapter 3 (seed 8000): tutorial (3 colors, size 3, 5 moves), 21 murky recipes with 4→6 colors and one-empty levels, then 8 murky recipes with one seal (6–7 colors). Measured scores: Ch. 2 tutorial 15, then 24 → 53 (mean 38.8); Ch. 3 tutorial 15, then 28 → 54 (mean 38.2); Ch. 1 ends at 52 and Challenger averages 56.5. The score ignores hidden information, so murky recipes play harder than their number. Full regeneration takes about 90 s.
93. **`levelgen --report DIR`.** Reports every `*.json` in a folder, prints min/mean/max and the score curve in file order, and exits with status 2 on any problem (minMoves mismatch, or a chapter lock that doesn't matter). The shipped-file test budget (#55) is unchanged: `swift test` solves only levels with a recorded search ≤ 8 000 states and checks their locks; the release report re-solves all 180 levels.
94. **Catalog from metadata.** `LevelCatalog` loads `chapter_*`, `challenge_*` and legacy `pack_*` files and splits them into `chapters` (by chapter number) and `challenges` (by file name) from the pack metadata (this resolves the open point in #90). A file without metadata falls back to its name: `chapter_NN` is chapter NN, anything else a challenge. A second file claiming the same chapter is skipped and reported. `catalog.packs` = chapters then challenges, which is the numbering `-LPOpenPack` uses (1–3 chapters, 4–6 Challenger/Expert/Master).
95. **Gate in the app = core rule.** `ProgressModel.unlockedChapters` feeds `progress(of:)` (clamped stars per recipe id) into `ChapterGate.unlockedChapters`; recipes use `ChapterGate.isRecipeUnlocked`. Stars saved for ids that no longer ship (`p4_`, `p5_`) are never asked for, so they're ignored without a migration. `-LPUnlockAll` opens chapters and recipes alike.

The map opens scrolled to the current chapter (`defaultScrollAnchor` at its spot — `ScrollViewReader.scrollTo` on `.position`ed markers was unreliable). Wide windows (≥ 760 pt) show the map as a framed column beside a panel (title, total stars, Continue, Challenges) over a blurred copy of the map; narrow ones fill the width with a Continue / Challenges bar as a safe-area inset. Closed markers use `allowsHitTesting(false)` rather than `.disabled`, which faded them on the Mac.

Unseen topics show once as an overlay (steps drawn with `BottleView`, so they look exactly like the game) and are marked seen on "Got it"; the "?" in the HUD (⌘/) shows the current recipe's topics any time. The seen-state sits behind `TutorialStore` (UserDefaults, one key per topic). Random Brew recipes show tips too.

Location names come from the data (pack name or `ChapterOutline.plan`) and are not localized.
100. **A cleared recipe stays open.** `ChapterGate.isRecipeUnlocked(at:in:isCleared:)` opens a recipe when the previous one is cleared *or* the recipe itself is cleared. Stars earned out of order (debug launch args, or a future reorder of a chapter) are never hidden behind a lock while they still count toward the chapter total.
101. **Locked recipe cells are not `.disabled`.** On the Mac a disabled plain button greys its label out on top of the cell's own locked look, which made locks and numbers unreadable in light mode. Locked cells draw a dimmed primary on a denser material and ignore taps (`allowsHitTesting`), and the action is guarded too.
102. **Random Brew is themed like the other menus**: painted workbench backdrop behind the grouped form (hidden form background) and the Settings button in the toolbar.
103. **Lock strength stays at "+1 move" for now.** A review probe found that no shipped lock makes its recipe unsolvable when removed, and 26 of the 38 locks in chapters 2–3 add exactly one move beyond the key pour, so the #91 threshold is met at its minimum. Raising it (≥ 2 extra moves, or unsolvable without the lock) means regenerating Rune Vault and Misty Marsh; that is a design call left open (see PLAN R2 notes), not a bug.
104. **Stronger locks** (user choice; supersedes #103). `LockImpact.lockMatters` takes a `cost`: the moves a lock must add compared with the same recipe without that seal and key (`minimumCost` 2 = key pour + 1, `strongCost` 3 = key pour + a 2-move detour), or the recipe is unsolvable without it. Chapters 2–3 now require `strongCost` for every recipe after the tutorial (levelgen `Tier.strongLocks`); the tutorial recipes keep `minimumCost`. Rune Vault and Misty Marsh were regenerated with the same seeds and ids (c2_/c3_); their curves stay 15 → 53/54. Generating chapter 2 takes ~18 min because two-seal candidates rarely pass.
105. **Daily date = a UTC calendar day.** `DailyDate` (year, month, day) is built from a `Date` with a Gregorian calendar fixed to UTC, never the device calendar or time zone, so the puzzle changes at UTC midnight for everyone (#62). Day arithmetic (`next`, `previous`, `adding(days:)`, `weekday`) is pure integer maths on days since 1970-01-01; it encodes as its ISO string (`"2026-11-15"`), which is also the level id suffix.
106. **Weekly plan** (`DailyPlan.spec(for:)`, depends only on the weekday; all size-4 flasks, seals must matter at `LockImpact.minimumCost`):

     | Tue | Steady | classic | 5 | 2 | 0 | 13–16 | 14.7 | 33.6 |

Thursday's window is lower than Wednesday's because murky layers play harder than their move count. The difficulty pips (1–7) are an order, not a measurement: by `Difficulty` score the week has three steps (Mon < Tue–Thu < Fri–Sun); within a step each day adds a mechanic (Wed a seal, Thu murky layers; Sat a seal and ~1 more move than Fri, Sun murky layers on top of Saturday's setup). The score doesn't see murky layers, so Thursday and Sunday play harder than their score. `daily-v1` had Saturday at 6 colors / 17–21 (score 38.9, clearly easier than Friday) and Wednesday at 14–18 (no harder than Tuesday); `daily-v2` fixed both. Labels ("Monday · Gentle") are English in the core; the app localizes weekday and tier names itself.
107. **Daily generation, algorithm `daily-v2`** (v1 until the Wednesday / Saturday change in #106). Base seed = SplitMix64 finalizer of FNV-1a 64 over `"daily-v2|YYYY-MM-DD"`. Phase 1: up to 60 candidates `Generator.candidate(spec, seed: base + i)` that pass the usual checks (no presolved flask, solved within 300 000 states, minMoves in the window, every seal matters). Phase 2: 60 more without the window (seeds base + 1000 + i). Phase 3: 100 candidates of 4-color classic (seeds base + 2000 + i). Phase 4: a built-in 13-move level, so it never fails. Only state caps (no timeouts), no Set/Dictionary iteration order, no system RNG, and no score filter (the score needs a `log2` and a costly dead-end analysis), so a date gives a byte-identical level everywhere; meta holds seed, minMoves and statesExplored. With `daily-v2`, over 365 days from 2026-11-16 every day was found in phase 1 (at most 16 candidates). **Any change to the plan, generator, solver results or this procedure must bump `algorithmVersion`**; a golden test pins 2026-11-15 (Sunday: seed, layout, 23 moves) to catch accidental changes.
108. **Daily generation is cancellable.** `DailyPuzzle.level(for:)` / `generate(for:)` `throws` `CancellationError` when the calling task is cancelled, instead of returning a level: a cancelled solve reports "unknown", which would otherwise silently pick a different candidate than on other devices.
109. **Perfect solve = solver minimum without a hint.** Hints stay available on the daily, but using one forfeits "perfect" (the badge means you found the shortest brew yourself); the solve still counts for the streak and the calendar.
110. **Only today's puzzle counts.** A `DailyResult` counts only if `solvedAt` falls on the puzzle's own UTC date; past days can't be played or caught up, and a solve finished after UTC midnight doesn't count (the app should offer the new day's puzzle instead). Per date the *first* counted solve is kept (`DailyHistory.record` refuses later ones), so a replay can't turn a day into a perfect one. Results dated after "today" are ignored (device clock set back). Recording only moves forward: `DailyHistory.record` refuses a solve whose `solvedAt` is earlier than a saved one, so setting the clock back to a missed day can't fill a streak gap (the win card then says the clock is behind). Limit, accepted for an offline game: the device clock is trusted otherwise, so a player who sets it *forward* can solve future days early (and is then refused for the skipped real days until the clock catches up).
111. **Streak rules.** Current streak = consecutive solved UTC days ending today, or ending yesterday while today is still unsolved (it stays alive until the UTC day ends); best streak = longest run ever; plus total solved and perfect count. Pure (`DailyStreaks.stats(_:today:)`), independent of input order and time zone. Two results of one date with the same `solvedAt` (only possible in imported or merged data) are broken by a total order: the one with a hint, then the one with more moves, is kept.
112. **Daily timings.** Release (M-series Mac, `daily-v2`): 60 days from 2026-11-15 take 1.1 s in total, max 0.12 s for one day; over 365 days the slowest day took 0.28 s. Debug test build: 60 days in ~23 s, max 2.6 s (test bound 10 s). A phone is expected to be a few times slower, still well under a second typically.
113. **`DailyModel` owns "today".** It reads `DailyDate(now)` from the core, re-reads it when the scene becomes active and from a task that sleeps until the next UTC midnight (+0.5 s), so a new puzzle appears while the app stays open. The level is generated in a detached task (cancellation forwarded; the core then throws, #108) and cached for one date only; the Play button shows "Brewing…" until it is ready. Results are a `DailyHistory` behind `DailyStore` (UserDefaults key `daily.history.v1`, JSON; unreadable data loads as empty).
114. **Recording a daily win.** `GameViewModel(dailyLevel:date:daily:)` has no `ProgressModel`, so the daily never affects chapter stars. On the win it calls `DailyModel.record(date:moves:minMoves:usedHint:)` with the puzzle's own date and `solvedAt = now`; the outcome is `recorded` (first solve), `alreadySolved` (a replay; the first result stays and is what the card and Share show) or `dayEnded` (finished after that UTC day; the card says so and nothing is saved). Restart / Replay clears the outcome so a replayed win is checked again.
115. **What counts as using a hint.** `usedHint` is set when a hint move is actually shown (a "couldn't find a hint" flash doesn't count) and stays set for that puzzle date, also across Restart and across leaving and reopening the puzzle (and quitting the app): `DailyModel` saves the hinted dates (`UserDefaults` key `daily.hinted.v1`, ISO strings; dates before yesterday are dropped on launch), the game screen starts with `hintUsed(on:)`, and `record` ORs the saved flag in.
116. **Daily presentation.** The puzzle's flasks are shown in a fresh random order like every recipe (`startLevel` shuffles; the puzzle is the same). Tips follow the normal seen-state, so a murky or sealed daily shows its tip only to players who never saw it. Labels are localized in the app (`Weekday.localizedName`, `DailyTier.localizedName`, `DailyMode.localizedName`, `DailySpec.localizedLabel`); the calendar is Monday-first with two-letter column names from the catalog, and the month title / dates are formatted in UTC and in the Gregorian calendar (like the grid), so a day never shifts with the device time zone and the title names the grid's month even when the device uses another calendar.
117. **Share text** is spoiler-free: `Pourfect Daily YYYY-MM-DD · N moves (perfect) · 🔥 streak` (ISO date, so players in any time zone compare the same puzzle). It comes from the catalog, so it is localizable.
118. **Debug dates and fake results never reach real data.** `-LPDailyDate` shifts the model's clock by whole days (`clockOffset`), so "solved today", the countdown and `DailyResult.counts` behave as on that date. With it or `-LPDailySeedResults N`, the model uses `MemoryDailyStore`: nothing is saved.
119. **Undo doesn't forfeit "perfect".** A perfect solve compares the final move count (`GameSession.moveCount`, undone moves don't count) with the solver minimum, the same count the chapter stars use. A player can explore, undo back and then replay the shortest path, also on murky days (undo hides the uncovered layers again, but the player has seen them). That is accepted: "perfect" means the brew was finished in the fewest pours without asking for a hint; counting every pour would punish a single mis-tap. Revisit if a stricter "no undo" badge is wanted.
120. **Flask modifiers.** `Bottle.modifiers: [BottleModifier]` is a set (deduplicated, sorted in a canonical order on every write), stored compactly: no modifier and a lone seal need no array, so classic and sealed bottles copy as cheaply as before (an array-backed first version cost ~20 % solver time). `lockedBy` is a computed accessor for the `.sealed` modifier (get/set), so the app compiles unchanged. All R5 cases are defined now (`essence`, `narrowNeck`, `funnel`, `tap`, `frozen(layer:turns:)`, `bubbling(every:phase:)`, `cauldron([Recipe])`); only `.sealed` is implemented. Unimplemented modifiers, links and goals are rejected by `validate()` (`unsupportedMechanic`) and by the solver (`.unsupportedState`) instead of silently playing as classic flasks. A bottle with two seals is a validation error until multi-rune seals exist.
121. **One modifier pipeline.** `Rules.apply(_:as:to:source:target:)` is a single switch over (modifier, side) that sees both bottles and may veto a pour or change a `PourPlan` (`layer`, `limit`, `opensSeal`; R5 adds fields such as pour-from-bottom, #130); the base rule reads the plan's layer, not the source's top. `Rules.plan(from:to:)` runs source modifiers, then target modifiers, then the base rule, and builds no bottles, so legality checks (solver candidates, `canPour`) stay cheap; `transfer` applies the plan. `Rules.pour(from:to:)` stays public as the two-bottle view. The seal migration is checked against a verbatim copy of the old rules on up to 720 lock states (generator candidates and random walks).
122. **Frozen layers are a modifier with a layer index**, `.frozen(layer: i, turns: n)` (0 = bottom), not a `Layer` flag. Pours above it keep the index valid, but bubbling (bottom layer to the top), a tap (pours from the bottom) and cauldron mixing change layers under the top, so they would leave the index pointing at another layer. Open rule for R5 (D1 with D2/C4/E1 in chapter 10): either a frozen layer blocks those effects in its flask, or the timed step re-indexes `.frozen` modifiers; it must be decided and tested when D1 is implemented together with them. `Layer` stays a plain enum, so runs, equality and the 6-bit layer tokens are unchanged. The bubbling phase also lives in its modifier.
123. **Links and goal live on `GameState`** (`links: [Link]`, `goal: Goal`), referencing bottles by index, in one shared box that is nil for the default, so a classic state copies one more nil reference. Switch → gate is a link whose gate state is derived from the switch's content (no stored state). `GameState.permuted(by:)` / `shufflingBottles` renumber links and goal targets with their bottles (the classic shuffle is unchanged).
124. **`moveCount` is optional.** It is stored (and incremented by `resolve`) only when a rule needs it (a timed mechanic or the rescue goal); classic states keep nil, so states reached at different depths still share keys. When present it stops at `Rules.moveCountLimit` (one past the largest count a rule distinguishes: rescue `withinMoves + 1`; 0 when no rule reads it, so it never changes). An unbounded counter made the state graph infinite: the solver could never prove such a level unsolvable (it ran into `maxStates`) and never merged positions reached at different depths. A2 corks must raise the limit to their own bound.
125. **`Rules.resolve(_:afterAction:)`** is the turn: action → immediate effects (unseal) → move counter → timed effects (empty hook, fixed order corks → thaw → bubbling → evaporation → conveyor) → immediate effects again if a timed effect changed anything → goal check. It returns a `Turn` (state + `isWon`); `GameState.pouring`, the solver and the state graph use it. Unsealing moved from the pour itself to step 2: the pour reports the key it delivered and `resolve` opens the seal. Steps 2 and 5 call the same `applyImmediateEffects` (unseal first), so mixing and gates added there run after every pour, not only on turns where a timer fired. Step 1 is `actionPlan(for:in:)`, which `isLegal` (`canPour`, `legalMoves`) also uses, so the move list and `resolve` can't disagree when links add vetoes or extra pours. `GameState.isSolved` = `Rules.isMet(goal, by:)`.
126. **StateKey v2.** Classic and sealed states (no links, standard goal, no counter, at most a seal per bottle) produce exactly the v1 words (checked against the old packing and by golden fingerprints of every shipped level). Anything else: bottle groups (v1 word with an extension flag, then a count and modifier words) sorted lexicographically, then a marked global section with links, goal and move counter. Link endpoints and goal targets are written as the canonical rank of their bottle; bottles with identical groups are tied, and the rank assignment of tied bottles that gives the smallest global section is chosen, which makes the key canonical (permutation-invariant) and injective up to isomorphism. Past 720 tie assignments the bottles' own order breaks ties (still correct, less deduplication); the count saturates, so any number of tied bottles is safe (23 tied flasks with a link used to overflow `Int` and trap). A goal-target word is the bottle's rank in bits 56..<64 plus the layer tokens (bits 0..<54); it carries no layer count, which the non-zero tokens already give (a count at bit 48 overlapped a ninth layer). Release timing for an 8-color state: v1 0.16 µs per key, v2 with modifiers 1.0 µs, v2 with a link between tied bottles 2.1 µs; the classic solver is unchanged (bench `--colors 8`: mean 0.029 s before and after; `--colors 7 --locks 2`: 0.18 s before, 0.16–0.17 s after).
127. **The solver prunes only classic states.** The three pruning rules assume plain or sealed flasks of one capacity without links; any other state gets every legal move until its mechanic adds safe pruning. Cross-checked against the naive BFS with a move counter forcing the unpruned path.
128. **Level format v2.** Bottles gain `modifiers` (everything but the first seal, which stays `lockedBy`), levels gain `links` and `goal`, each written as an object with a `"type"`. `LevelLoader.encode` writes `version` = `requiredVersion` (2 only if a level uses one of these), so all shipped files re-encode byte for byte and `levelgen --preset all` regenerates them identically. `LevelLoader.decode` checks structure only (round-trips of not-yet-playable levels); `load` also validates. A version-1 file that uses v2 fields is rejected (`needsVersion2`); version 3+ is unsupported.
129. **`MechanicImpact`** generalizes the must-matter check: `instances(in:)` lists every seal, other modifier, link and non-standard goal; `matters` re-solves without one and requires the level to become unsolvable or to lose at least `cost` moves (default `minimumCost(of:)` = inherent cost + 1: 2 for a seal, whose key pour is its inherent cost, 1 otherwise; callers may ask for more, e.g. `LockImpact.strongCost`, #104). `LockImpact` (with its `cost` parameter from #104) is now its seal case with identical results; `levelgen --report` checks every instance of a chapter level (one warning per instance).
130. **What R5 still has to restructure** (R4 review, deferred on purpose: each change is only testable with its mechanic). (a) *Pours on more than two bottles*: twins, overflow into a full flask and gates are checked and applied in `Rules.actionPlan(for:in:)`; `Transfer` then becomes a list of bottle changes, and the base rule reads new plan fields (`fromBottom` for a tap, `acceptsMismatch` for a cauldron partner, an overflow target) instead of assuming a two-bottle top pour. (b) *Turn events*: `Turn` carries only the new state; the app rebuilds each pour by diffing (`GameViewModel.startPour`: amount from the layer count, color from the source top). Before the first mechanic whose effect isn't a single top pour (tap, twins, overflow, mixing, timed effects), `resolve` must report what it applied (pour segments and effect events) and the app animate from that; recording events only when asked keeps the solver path free of allocations. (c) *Murky reveal state*: `GameSession.hiddenDepths` counts hidden bottom layers and assumes layers only change at the top. Bubbling (D2, which chapter 7 pairs with murky B1) and a tap break that (a rotation would hide a revealed layer again and show a hidden one on top). With D2 or C4 the reveal state moves into the rules: a per-layer hidden flag (or layer identity) that `resolve` carries through rotations and bottom pours; it then also enters `StateKey`, since the solver must not see hidden layers.
131. **R4 rebased on stronger locks.** R4 was branched before #104; after merging main, `MechanicImpact.matters` takes the cost (default inherent + 1, i.e. `LockImpact.minimumCost` for a seal, the old "+1" rule) and `LockImpact.lockMatters(cost:)` is its seal case, so `strongCost` recipes, the daily puzzle and levelgen behave exactly as on main. The no-behaviour-change evidence was re-gathered against main (`495eee2`): generator, random-level and solver golden fingerprints unchanged; the shipped-keys fingerprint was re-recorded from main's own pre-R4 code on the regenerated chapters 2–3 and matches; every shipped file re-encodes byte for byte; the daily golden level (2026-11-15) and all chapter lock checks pass; bench `--colors 8` and `--colors 7 --locks 2` return the same moves and states as before R4 and are not slower (#126).
132. **Essence flasks (C1), rules as implemented.** `.essence(c)` is one arm of `Rules.apply`. As a *target* it vetoes every layer but `.color(c)`: other colors and keys are refused even by an empty essence flask. The only exception is the key of its own seal: modifiers run in canonical order (seal tag 1 before essence tag 2), so the seal accepts its key first (`plan.opensSeal`) and the rune lets that pour through; unsealing (step 2 of `resolve`) removes only the seal, the rune stays. A sealed essence flask refuses its own color until it is opened (sealing rules apply first). As a *source* it changes nothing: it may start with mixed layers, which pour out normally (whole run, partial pours by free space). The goal is unchanged (`.standard`, `blocksSolved` is false): an essence flask counts as sorted when empty or full with one color. Since it can't receive another color, "full with one color" is its own color unless it *starts* full of another one; instead of a goal rule, `validate()` rejects that start (`essenceFullOfOtherColor`, #135), so no level can be won with a rune flask holding a foreign color (the generator also rejects it as a presolved flask, `isPresolved`). No counter, no layer state: undo/restart need nothing new (the session's state history already holds the modifiers).
133. **Solver pruning with gate modifiers.** A *gate* modifier (`BottleModifier.isGate`: seal, essence) decides only what a flask accepts; it doesn't change how many layers move or from where. The three pruning rules now run on any bottles-only state whose flasks carry only gates, with "interchangeable" narrowed to *alike* flasks (equal modifier sets): rule 3 tries only the first empty unsealed flask of each modifier set; rule 2 skips a whole-content pour only into an empty flask alike to the source (a plain flask's finished color poured into its empty essence flask is a real move and is kept); rule 1 (skip a full single-color source) applies only to a plain source while no empty flask carries a modifier. For classic and sealed states these are exactly the old rules (same code path, same results: golden solver fingerprints unchanged). Checked by a test that the pruned candidates reach every distinct canonical child of all legal moves (pruned moves lead only to the state itself), against the naive BFS on 175 random essence levels (with 0–2 seals), and against the unpruned path. `candidateMoves` calls `Rules.plan(from:to:)`, which for a bottles-only state is exactly `actionPlan` (the one legality check, #125) without its index checks (calling `actionPlan` there cost ~8 % solver time).
134. **StateKey fast path for one-word modifiers.** An essence flask takes the state off the v1 path (#126), and the general v2 encoding (one array per bottle, lexicographic sort of groups) doubled solve time. `StateKey.pairCodes` handles bottles-only states where every bottle has at most one non-seal modifier encodable in one word: it sorts `(v1 word, modifier word or 0)` pairs, which orders exactly like the groups (a group's first word decides unless both carry the extension flag; modifier words are never 0), and writes the same codes. A test compares it with `extendedCodes` on ~380 random essence states (with seals); a cauldron (several words) or anything with links/goal/counter uses the general path. Release, 10 seeds, M-series Mac: `--colors 8 --essence 1` 0.049 s mean before the fast path, 0.019 s after.
135. **Validation for runes.** `multipleEssences(bottle:)` (two runes on one flask could never receive anything) and `essenceColorAbsent(bottle:color:)` (a rune of a color the level doesn't contain; also covers negative or out-of-range ids, which `StateKey.canEncode` would reject) and `essenceFullOfOtherColor(bottle:color:)` (a rune flask that starts full of one other color would count as sorted, #132). A rune on a flask that starts with other colors, or on a sealed flask, is valid.

181. **(Superseded by #212–215: pressure pipes.) Deviation: an overflow pipe matters by the spill it can force, not by a cost.** The task asked for a cost-based must-matter check like strong locks. Measured: in ~10,000 random levels (3–5 colors, sizes 3–5, 1–2 empty flasks, every placement, and arbitrary partly filled boards), removing a pipe never changed the optimal length, not once. Reason: the only new pour is "fill `a`, the rest into `b`", which leaves `a` full with that color on top but *not* sorted (all of a color is `capacity` layers, and some are in `b` or still in the source), so those layers must leave `a` again; the same result costs the same as pouring the run into `b` directly. A full `a` passing the pour on equals a direct pour into `b`. What a pipe *can* do is spill: a pour into `a` that the player wanted to stop at `a`'s rim also fills `b`. So, like a funnel (#150), a pipe matters when it sets a trap: `MechanicImpact.spillDepth(of:in:)` finds a pour from a still-solvable position that loses the level while the *same pour without the pipe* doesn't (it replays the pour on the position with the pipe removed; only pours the pipe changes are re-solved, at most 40, graph ≤ 300k states). `MechanicImpact.matters` accepts a pipe whose cost reaches the asked cost (either way, `isTwoSided`) *or* that sets such a spill. Spill traps are rare: ~1 in 150 random 6-color size-3 boards with two empty flasks and the pipe from a filled flask into an empty one (`LinkPlacement.mixed`), almost never with fewer colors or bigger flasks, so the chapter's pipe recipes all use that shape, and each costs ~50 s to find. **Open design question for the user:** as decided, the pipe is a pure hazard that a careful player never sees work. A rule change that would make it a real tool, e.g. "the rest flows into `b` whatever `b`'s top color" (a way to bury or park layers), would need a new decision.

192. **Mixing cauldrons (E1), rules as implemented.** `.cauldron([Recipe])` (1...`Rules.maxRecipes` = 2 recipes `a + b → result`, stored sorted; JSON `{"type": "cauldron", "recipes": [{"a": 0, "b": 1, "result": 4}]}`) has two arms in `Rules.apply`. As a *source* it changes nothing. As a *target*, when the plan's layer is a color `x`, the cauldron's top layer is another color `y` and a recipe mixes `{x, y}`, it marks the plan (`PourPlan.mixIndex`, the recipe's index) and the base rule accepts `x` on `y` (otherwise empty, same color, no recipe or a key: the usual rule). The amount is the usual `n = min(run, free space, limit)` (a narrow neck or tap on the source applies as everywhere), and `p = min(n, m)` pairs mix, where `m` is the cauldron's top run of `y`: `[…, y×m] + x×n → […, y×(m−p), z×2p, x×(n−p)]`. Each poured layer that mixes takes one layer of the run below; the result layers sit where the mixed part of the run was, the rest of the run stays below them and unmixed poured layers stay on top. Layers are conserved. **Nothing chains**: the new layers never mix with what lies below or above until another pour lands on them, and `validate()` rejects a recipe whose result is another recipe's ingredient (`chainedRecipes`), so a result never sits on its own partner. With layers leaving only from the top, play therefore never leaves an ingredient directly on its partner inside a cauldron (`Rules.holdsUnmixedPair`), and a level may not start with one (`unmixedPair`): it would read as a broken rule. **Turn order**: the task put mixing in step 1 (with the pour, before the timed effects); MECHANICS §4 and #125 had it in step 2. It is applied by `transfer` together with the pour (it needs how many layers landed on which run, which only the pour knows; the step-2/5 rerun of `applyImmediateEffects` has nothing to mix) and reported as `TurnEvent.mixed(bottle:recipe:pairs:)`, always the turn's first event, before any `.thawed` / `.bubbled`. Outside a cauldron nothing changes; pours out of a cauldron are normal. The win is standard: a cauldron ends empty or full of one color (`blocksSolved` is false). A cauldron carries no other modifier (`cauldronCombined`, so ice never sits on recolored layers, #122) and is no link end (`linkedCauldron`: a linked pour never mixes). Undo/restart need nothing new (no counter; the session's history holds the unmixed layers). Murky masks need no extra step either: mixing keeps the layer count and only touches the cauldron's top run (always in view) and the layers that just landed (visible), so the masks after the pour are already right (tested).

229. **Customer orders: the rules (R7).** Two goals are implemented, both through `Rules.isMet` (the win check of `Rules.resolve`, the session and the solver all go through it): **order** (`Goal.order`): each marked flask must end full (`capacity` layers) of its potion, without a seal or ice on it (`blocksSolved`, as for any solved flask); every other flask is standard-solved. A **partial order** is simply an order that marks some flasks: no separate case. **Layered recipe** (`Goal.pattern`): each marked flask must end with exactly its layers, bottom to top (`capacity` color layers, two or more colors); every other flask carries nothing that blocks, holds one potion or nothing, and for each potion at most one unmarked flask holding it is not full. So the remainder of a potion the recipe used (e.g. red 2 of 4 in the pattern → 2 red left) is gathered in one partly filled flask, and a potion with whole flasks' worth fills them, which is the standard rule again. The same rule is never needed for orders (every potion has whole flasks left), so `.order` stays exactly "targets + standard". Validation (`goalErrors`): every target names a different existing flask without a tap, asks for exactly `capacity` color layers (an order: one color); the targets want no more of a potion than the level holds; targets + one flask per whole `capacity` of each remaining potion + one per partial remainder fit in the level's flasks. A layered recipe with a cauldron is rejected (`layeredWithCauldron`: mixing changes counts, the remainder rule isn't defined there); an order with a cauldron is allowed (only the structure is checked; the solver decides). Display helpers: `Rules.isTargetMet`, `Rules.metTargets(in:)`, `GameState.goalTarget(at:)` / `isTargetMet(at:)`, `GoalTarget.order(bottle:color:capacity:)`, `.color`, `.isLayered`, `.runs`; `LevelDefinition.mechanics` names `.order` / `.layered`, `isCustomerOrder`. JSON v2 kept its R4 form (`{"type": "order"|"pattern", "targets": [{"bottle": n, "layers": […]}]}`); the target indices follow their flasks through `permuted(by:)` and shuffles. **Rescue** (free all seals within N moves) is dropped by the user's decision: it stays defined (decodes) but is not implemented and never validates.
230. **Orders in the solver and the key.** `Solver.candidateMoves` marks every target flask like a linked flask: it is never *alike* another flask, so an empty target is a target of its own (rule 3), its presence turns rule 1 off (a full one-color flask may have to move into the flask that ordered its potion: rule 1 would have skipped it as finished), and a target source is never relocated (rules 1, 2). Rules 2 and 3 only permute unmarked flasks, which the goal treats alike; rule 1's premise (a full one-color flask holds all of its potion) holds for orders and layered recipes (no layered recipe with a cauldron; with a cauldron rule 1 is off anyway). The twin rule is dropped for a pair with a marked twin. Unlike links, marks keep the pruning with ice or bubbling (a relocation or wait between unmarked flasks is the same permutation); the bubbling "one wait per state" rule now also requires an unmarked source (found by the pruning test). `StateKey.linkedCodes` takes goal states too: a target's role holds its layer bits (above the five link-role bits, plus a flag bit), so a marked flask never ties with an unmarked one or a target that wants something else, and the targets are written by canonical rank (`untiedTargetWords` when no target is tied, else the permutation search). Cross-checked against the naive BFS on random small order and layered levels with seals, runes, glass, ice, bubbling, twins, pipes, switches and a cauldron, plus positions a few moves on; the pruned list reaches every distinct child. Orders cost ~1.7× per state (7 vs 4 µs) and explore about twice the states of the same board without the order; classic and lock benches are unchanged (`levelgen --bench`, within noise).
231. **Must-matter for orders (`OrderImpact`).** With whole flasks of every potion, every won position of an order is a standard win, so the level without the order is never longer: the order *matters* when the optimum with it is at least `cost` moves longer, i.e. no standard-optimal solution happens to leave the ordered potion in the ordered flask. The chapters use cost 2 (`OrderImpact.strongCost`) after chapter 2's tutorial (cost 1). A layered recipe can never be met by a standard win (its flask holds two or more potions), so every standard-optimal line fails it: it always matters (`MechanicImpact.matters` short-cuts it). `levelgen --report` checks the goal like every other mechanic instance of a chapter recipe.

## R9 — Ingredient gathering (match-3)

251. **Scope and architecture.** Optional match-3 episodes (user-approved): one after each sorting chapter 1–10, 8 levels each. The rules are a new library target `Match3Core` in the `BottleSortCore` package (pure Swift; depends on `BottleSortCore` only for `SplitMix64`, `DailyDate`/`Weekday` and `DailyResult`), with the executable `m3gen` and the test target `Match3CoreTests`. The sorting rules pipeline (`Rules.swift`) is untouched; every match-3 rule is in `Match3Core/M3Rules.swift` (pure board functions plus the `M3Game` extension that applies start board, waves, gravity, refill, reshuffle and finale), `M3Game.swift` only holds state and the turn order. Original naming throughout: ingredients mushroom, crystal, feather, moonflower, ember, potion drop; specials *comet* (row / column), *bloom* (3×3), *prism* (one kind); finale *Bubbling Over*; obstacles frost, sealed crates, potion flasks.

252. **Board.** At most 8×8, row 0 at the top, gravity towards higher rows. A cell exists or is a hole (layout `.`); an existing cell holds nothing, a piece or a flask, or is a sealed crate with 1–3 hits left (then it holds nothing). Frost belongs to the piece (`M3Piece.frost`, 0–2 layers) and moves with it. A prism has no kind. A cell is *open* when it exists and has no crate; each column's open cells, top to bottom, are its gravity stack.

253. **Swaps and matches.** A swap drags the piece at `from` onto the orthogonal neighbour `to`. Legal when both cells hold unfrozen pieces (not flasks) and either one is a prism, both are specials (comet/bloom), or the exchange makes a run of 3 through one of the two cells; otherwise it is refused (no move used, nothing changes). Runs are maximal straight lines of 3+ pieces of one kind; frozen pieces and comets/blooms count with their kind; prisms, flasks, crates, holes and empty cells break runs. Runs sharing a cell form one group (row-major order of first cell). Special per group: a run of 5+ → prism; else crossing runs (L, T, +) → bloom; else a run of 4 → comet; a run of 3 → nothing. Placement: the swap's `to` cell if in the group, else `from`; in a cascade a bloom goes to the lowest (then leftmost) crossing cell, the others to the lowest (then leftmost) group cell; frozen cells are skipped (none unfrozen → no special). A swap-made comet clears along the swap's axis (horizontal swap → row); a cascade comet clears across its run (horizontal run → column).

254. **Clear waves.** Unfrozen group cells are cleared (`match`); frozen group cells lose one layer and stay. Every cleared special fires once, in queue order (combo seeds first, then specials in the order they were cleared): comet row/column, bloom 3×3, prism the most common kind among unfrozen pieces not already being cleared (ties: lowest kind index; none left → it just goes). An effect clears every unfrozen piece it reaches (`blast`), takes a layer off frozen pieces, hits crates and passes flasks by. Each cell cleared by a match also hits frost and crates on its four neighbours; blasts don't spread. Every frozen piece and crate takes at most one hit per wave. A crate at 0 becomes an empty open cell; frost at 0 frees the piece in place. New specials are placed last, so they never fire in the wave that made them. Special swaps (wave 1, both pieces used up as `combo`, effect at `to`): comet+comet → row and column (`cross 1`); comet+bloom → three rows and three columns (`cross 3`); bloom+bloom → 5×5; prism+plain X → every X; prism+comet/bloom of kind X → every unfrozen plain X becomes that special (comets alternate row/column by `(row+col)` parity) and every unfrozen X fires in row-major order; prism+prism → every cell. Collect goals count every cleared piece of the kind, specials included.

255. **Gravity, refill, flasks, determinism.** After each wave: every column's pieces and flasks (frozen pieces too) drop straight down to the lowest free open cells, keeping order, sliding behind crates and across holes; nothing slides diagonally in v1. Then refill from the level's single `SplitMix64(seed)` stream: first flasks — while `flasksSpawned < drops.total` and fewer than `drops.maxOnBoard` are on the board, one goes to the top empty cell of a column drawn uniformly from the allowed columns that have one; then every remaining empty open cell gets a uniform kind from `kinds`, columns left → right, cells bottom → top. A flask on its column's lowest open cell is collected (then settle again). Stream order over a game: start board, each settle, reshuffles, finale — so the same swaps always give the same boards. Start board: placed pieces, then seeded cells column by column bottom up, each kind uniform among those that make no run of 3 with what is already there (all kinds if none); rejected (stream continues, up to 200 tries) until no match and a valid swap. Spawn records carry `rank`/`columnCount` so the app can start them above the column.

256. **Turn, scoring, goals, stars, finale.** An accepted swap uses one move: swap → wave 1 → (settle → collect → settle …) → cascade waves until stable (cap 200) → win / loss → reshuffle. Points: 30 per cleared piece × min(cascade, 5); 40 per special fired; 60/90/150 for a new comet/bloom/prism; 50 per frost layer or crate hit; 500 per flask. Goals: collect N of a kind, all frost layers, all crate hits, N flasks (= `drops.total`), a score. Won when all goals are met after the cascades; lost at 0 moves otherwise. Stars: 0 if lost, else 1, 2 at `stars.two`, 3 at `stars.three` (final score incl. finale). *Bubbling Over* finale (`playFinale`, after a win): each leftover move draws a plain unfrozen piece (uniform over the row-major list) and a special (row comet / column comet / bloom, uniform), fires it at once with normal cascades, +100 per burst.

257. **Reshuffle and hint.** If a turn ends without a valid swap: up to 60 Fisher–Yates rearrangements of all unfrozen pieces (specials included; frozen pieces, flasks, crates stay) from the stream, the first with no match and a valid swap wins; else up to 60 re-rolls of plain unfrozen pieces' kinds with the start-board rule; if both fail the game is lost (never seen). `hint()` returns the valid swap with the best one-wave value for the current goals (the bot's value, first in row-major order on ties); free, never costs stars.

258. **Step result for the app.** `M3Game.play(_:)` returns `M3StepResult {swap, accepted, phases, scoreGained, movesLeft, status}`; `phases` in order: `.swap`, `.wave(M3Wave)`, `.settle(M3Settle {falls, spawns})`, `.collect([pos])`, further waves…, `.reshuffle(M3Reshuffle {moves, rerolled})`. `M3Wave {cascade, groups (cells, shape, creates, createdAt), conversions, activations (at, special, effect, cells), cleared (at, piece, cause match/blast/combo, activation index), frostHits, crateHits (at, remaining), created, score}` — animate in that field order. `playFinale()` returns `M3Finale {bursts (at, special, phases, scoreGained), scoreGained, finalScore, stars}`. `preview(_:)` gives wave 1 of a swap without playing it.

270. **Distillery: scope and architecture (R10).** The pipe-rotation puzzle is its own game, so its rules live in a new pure library target `DistilleryCore` (same package, depends only on `BottleSortCore` for `ColorID`, `SplitMix64`, `DailyDate`, `DailyResult`; no UI frameworks) with the `distillgen` tool and the `DistilleryCoreTests` target. The sorting rules in `Rules.swift` are untouched; inside the distillery the rules are single-sourced in the same spirit: one evaluator (`DistillNet`, used by `DistillFlow.evaluate`, the win check, the solver's leaves and the brute-force reference). Sources (cauldron outlets) and targets (flasks) sit on their own grid cells (the generator puts them on the rim, facing in), so a 7×7 board is the whole play area; the board is 3…7 cells per side. Pieces: empty cell, end cap, straight, elbow, tee (one junction), cross (two independent pipes); a piece can be riveted (`fixed`), carry a valve (linked to a target) or a heat coil (`from → to`). Rotation is clockwise quarter turns from the base orientation (cap N, straight N–S, elbow N–E, tee N–E–S).

271. **Flow rules.** The flow of a static configuration is a breadth-first fill from every source at once, one step per channel (a cross has two channels, everything else one). Liquid passes between two cells only through facing openings. A target flask takes liquid in and passes nothing on; a cap ends a line without leaking; a heat coil passes its `from` color on as `to` (other colors unchanged; its entry sides keep the incoming color, the others carry the heated one). *Murk:* a channel reached in the same step by two colors turns murky and passes nothing on (it blocks); two wet channels whose facing sides hold different colors meet in a murky *seam* (reported as cell + side). *Leak:* a wet channel's opening that faces the edge, an empty cell or a side without a facing opening drips (reported with color and tick). *Valves* are a fixpoint: all start shut; a shut valve takes liquid in up to its gate on each side (never murky, never leaks) and passes nothing; after each evaluation every valve whose linked flask holds its own color (clean) opens and stays open (latched); evaluate again until nothing opens (≤ valves + 1 passes). *Won:* no leak, no murky channel or seam, every target holds exactly its own color. Unconnected dry pieces are allowed (simpler, and decoys may then lie any way). Consequence used by the solver: at a win every valve is open (a still-shut valve would mean its flask is not full), so the winning flow equals the all-open flow; a valve only rules out networks whose flask order deadlocks (a flask fed only through its own valve). For the app every channel reports `liquid`, `sideColors`, `entry` sides and a `tick` (first wet step, counted on across valve stages), plus `leaks`, `seams`, `received` per flask and `valveOpenedAt` (stage).

272. **Taps, undo and stars.** A tap turns a piece a quarter clockwise; a long-press / right-click a quarter counter-clockwise; both count one tap. So a piece that needs k quarter turns clockwise costs min(k, 4 − k) taps, and a straight's two equal orientations count as one. Tapping a riveted piece, a cross (turning changes nothing), an empty cell, a source or a flask does nothing and isn't counted. No tap limit: every level is finishable. Undo takes the last tap back and the count goes down (like `GameSession.moveCount`, #7); Restart resets to 0; after the win the board is frozen (no taps, no undo). Stars by the final count: 3 at `minTaps`, 2 within `2 + minTaps / 5` more (a wrong turn costs two taps, there and back), else 1 (`DistillStars`).

273. **Exact solver.** A solution is described by its *network*: the wet pieces and their openings; dry pieces may stay as they are and cost nothing. The search grows a closed network from every source outlet and flask inlet: each placed piece's openings must face openings of placed neighbours (a riveted / cross / source / flask cell is constant and joins as soon as something opens towards it); it always places the pending piece with the fewest fitting orientations (MRV), so forced pieces cost no branching. Pruning: leaks; color labels joined along coil-free stretches from sources and flasks (two colors in one stretch fail; coils separate stretches, so the pruning stays sound); when minimizing, taps so far + the cheapest fitting orientation of every pending piece ≥ best. Every finished network is checked with the full evaluator, so valves, coils and murk are exact. `solve` counts networks up to a limit (2 = uniqueness) and, if there are more, runs a branch-and-bound pass for the minimum; `minTaps`, `hint` (first piece row-major off its solved orientation, turned the shorter way). Node limits only, no clock (deterministic). Cross-checked against brute force over every rotation on 300 random tiny boards with every mechanic (`DistillSolver.reference`). Speed: shipped 7×7 levels 0.05 ms mean, 0.11 ms max (release, `distillgen bench`).

274. **Generator and difficulty.** Per attempt (seeded stream, arrays only, deterministic): sources and flasks on rim cells facing in, kept apart; one network per source (own color): a main path from the outlet through 0–2 random waypoints to the first flask, then a branch from each further flask's inlet back to a two-opening pipe of its network (which becomes a tee). Routes are Dijkstra over cells with random step costs and a turn cost, and may jump straight across another route's straight pipe at a right angle (a cross; cheaper when crossings are wanted). Then cap stubs (a tee branch ending in a cap), colors (distinct; a coil network takes red / blue / yellow), heat coils on a two-opening pipe with flasks below it (those flasks want the heated color: red → orange, blue → purple, yellow → green, never two coils on one path), valves on a pipe with flasks below, linked to a flask not below it, rivets on network pieces, decoys on `decoyFill` % of the free cells (shape list = weights), some riveted. The solved board must win (no valve deadlock). Uniqueness: count networks (limit 2); while there is a second one, change a decoy it uses (another shape, then empty) or, if allowed (`repairWithRivets`), rivet a network piece where they differ; up to 16 repairs. Then scramble: random rotations, adjusted one quarter at a time until the taps hit a value drawn from the window (unique network ⇒ that is the minimum; the solver confirms). `minNetwork` rejects short routes. Difficulty score = minTaps + 3·decisions (solver branch points) + 2·mechanics + network pieces / 3 + decoys / 4. `distillgen` builds it in release.

275. **Level format.** File: `{"format": "pourfect-distillery", "version": 1, "id", "title", "levels": […]}`, pretty-printed with sorted keys; a newer version or another format is refused. Level: `id`, optional `title`, `width`, `height`, `grid` (one string per row, space-separated tokens: `.` empty, `S` source cell, `F` flask cell, `X` cross, else a shape letter `C`/`I`/`L`/`T` + rotation digit; trailing `*` = riveted), `sources [{r, c, color, dir}]` (`dir` = outlet n/e/s/w), `targets [{r, c, color, dir}]` (`dir` = inlet), optional `valves [{r, c, target}]` (target index) and `coils [{r, c, from, to}]`, `minTaps`, optional `stats {seed, networkCells, decoys, decisions, nodes, mechanics, score}` (informational). `validate()` checks sizes, tokens vs. source/flask entries, cells, facing the board, palette colors (0…11), valve links, valve/coil only on straight / elbow / tee, no coil keeping its color, minTaps ≥ 1; `validateSolving()` adds the solver: solvable, `minTaps` matches, one network.

276. **Distillery content.** Five files in `Levels/distillery/` (names unique in the app bundle): `distillery_stage_01.json` *The Cold Still* (`d1-01…20`; 4×4 then 5×5, one cauldron and one flask, straights and elbows, decoy caps, riveted decoys at the end; 3 → 14 taps), `distillery_stage_02.json` *Copper and Steam* (`d2-…`; tees from 1, riveted pieces from 5, two colors from 9, crossings from 13, all mixed with cap stubs 17–20; 5×5 → 6×6; 6 → 20 taps), `distillery_stage_03.json` *The Great Alembic* (`d3-…`; heat coils from 1, valves from 5, then two colors with coils / valves / crossings / rivets on 7×7, three colors at 19–20; 10 → 29 taps), and the Challenges packs `distillery_expert.json` (`dx-…`, 6×6 → 7×7, two to three colors, every mechanic; 17 → 28 taps) and `distillery_master.json` (`dm-…`, 7×7, up to three colors, valves and coils in every level; 24 → 38 taps). Every slot of a preset (`DistillContent.slot`) generates 12 candidates from consecutive seeds and keeps the one whose score is closest to a linearly rising target, so each quarter of a pack is harder than the one before (tested). `distillgen packs` rewrites all five byte-identically in ~1.5 s.

277. **Distillery in the game.** Its own wing on the chapter map with the three workshop stages: stage 1 opens with chapter 3, stage 2 with chapter 6, stage 3 with chapter 9 (`DistillProgression.openingChapter = 3·n`; the stages then sit beside the matching chapters and each starts when the sorting game has taught enough patience for its size). Optional: never blocks a sorting chapter; its stars live in their own store (the `d1-…`, `dx-…` ids) and never count towards a chapter gate (cosmetic milestones would be fine but none are added in core). Levels in a stage open in order. Each stage opens with a story scene, id `distillery.N` (`DistillProgression.sceneOnOpening`); `StoryScene` in `BottleSortCore` is not extended here, because the app switches over it exhaustively: the app adds the case with its lines. Challenges: Expert and Master packs, and Random Distillery (`DistillRandom.level(tier:seed:)`, tiers Gentle 5×5 / Tricky 6×6 two colors / Fiendish 7×7 with valve and coil; same seed, same level).

278. **Daily Distillery.** `DistillDaily`, generator id `distill-daily-v1`, level id `distill-daily-YYYY-MM-DD`: seed = FNV-1a of `distill-daily-v1|date` mixed once; 4 candidates from consecutive seeds, the score closest to the weekday target wins (Monday Gentle 5×5 one flask → Tuesday Splitter → Wednesday Two Colors 6×6 → Thursday Heat Coil → Friday Valves → Saturday Crossings 7×7 → Sunday Grand Still 7×7 with valve, coil, crossings and two colors); if all fail, Monday's settings with more attempts (never seen). Integer maths and node limits only, so every device builds the same level; 1–16 ms per day in release (365 days in 1.4 s). Own streak and stats through `DailyStreaks` (`DistillDaily.result`: perfect = minimum taps without a hint; the app keeps its own store). `DistillDaily.fingerprint` hashes the board for golden tests. The Daily Brew and Daily Gathering generators are untouched (their goldens still pass). The single "Today" card / daily hub on the map is app work.

279. **Distillery tests and speed.** `DistilleryCoreTests` (45 tests): flow for every piece, crossings vs. junctions, murky channels and seams, leaks, caps, valves (open, deadlock, wrong color), coils (heated, unchanged, heated meeting raw), dry pieces; taps, undo, restart, frozen win, stars; solver cases (ccw, rivets, deadlocked valve, forced coil route, hint walk = minimum) and the brute-force cross-check; generator windows, uniqueness, determinism, coil colors, random tiers; every shipped level valid, unique and at its recorded `minTaps`, stages teaching in order, rising quarters, packs harder in order, packs regenerating byte-identically; daily goldens (9 days), a two-month sweep rising by weekday, the streak result; format round trip and refusals; progression. Heavy ones (byte-identical packs, golden days, the sweep, the full 300-board cross-check) run optimized and in a debug build only with `LP_SLOW_TESTS=1`.

280. **Distillery board in the app (R10 app part 1).** `Pourfect/Distillery/`: the game (`DistillGame`) is the only truth; `DistillBoardModel` plays each tap at once and only times what the board shows: the turned piece spins for 0.16 s (its liquid hidden meanwhile), channels that became wet fill one 0.07 s step per core `tick` after it lands (so liquid runs from the sources along the new path, valve stages included), channels that ran dry drain at once, and a flask fills when its liquid arrives. Input is never locked; a second tap mid-animation starts from the displayed angle. Everything is drawn in one `Canvas` (`DistillRenderer`, `DistillArt`) inside a `TimelineView` that runs while something moves (and at 30 fps while drips fall or murk drifts; paused under Reduce Motion, where turns and fills are instant). Pieces are drawn in their base orientation in a rotated context; liquid takes each side's color from `sideColors` (so a coil's exit sides show the heated potion). Targets reuse `BottleView` (capacity 3: two layers when the right potion arrives, the third plus cork and sparkle at the win). Sources and wanted-color tags always carry the color rune (they are markers, not liquid). Valves show a red / green handwheel and a number tag matching their flask's; coils a copper winding that glows hot while liquid passes and a "from → to" tag. Murk is a dull puff with a red ring; leaks a drip falling from the open end. *Hint:* turns one piece a quarter toward the cheapest solution from the current board (`DistillGame.hint()`, off the main thread); it counts as a tap and caps the attempt at two stars (Restart gives the third back), like the sorting hint costing the perfect result. *Controls:* tap / click = clockwise; touch-and-hold, right-click, Option-click or Control-click = counter-clockwise; ⌘Z undo, ⌘R restart, ⇧⌘H hint, ⌘/ tips. Tips (`TutorialTopic` `distill.*`): basics until seen, then splitters, riveted pieces, two potions (murk), crossings, heat coils and valves the first time a level has them, drawn as small still boards. VoiceOver reads each cell (piece, open sides, riveted, valve / coil, what it carries, leaking, row and column; cauldrons and flasks with their potion) with a counter-clockwise action. Best stars and fewest taps per level id in `DistillProgressModel` (`distill.bestStars.v1` / `distill.bestTaps.v1`), never read by sorting gates; random levels save nothing; the daily hands its result to the caller (`onWin`) for its own store.
