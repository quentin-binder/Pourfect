# Decisions

Short entries, newest at the bottom.

1. **Repo layout.** The repo root is `LiquidPour/` (not `BottleSort/`). The existing Xcode project `LiquidPour.xcodeproj` and its folder `LiquidPour/` play the role of the spec's `App/`. `Packages/BottleSortCore` and `Levels/` sit at the repo root as specified.
2. **No XcodeGen.** XcodeGen isn't installed and the user already created the Xcode project, so we keep it and make small targeted edits to `project.pbxproj` (user-approved) instead of generating one.
3. **Platforms.** App target supports iOS/iPadOS and native macOS (arm64 + x86_64 universal, via SwiftUI multiplatform — not Catalyst, not "Designed for iPad"). visionOS removed. Minimum iOS 17 / macOS 14 (matches the package platforms and `@Observable`).
4. **Git.** Commits go directly on `main` (user choice). Per-user Xcode state (`xcuserdata`) is ignored.
5. **Tooling.** Package uses swift-tools-version 6.0 (Swift 6 language mode, strict concurrency; all model types are `Sendable` value types). Tests use Swift Testing (`import Testing`), which ships with the toolchain — no third-party deps.
6. **Rules in one place.** `Rules.pourAmount(from:to:)` is the single legality + amount check (returns 0 = illegal); `Rules.movableRunCount` and `Rules.isSolved` are the other hooks. `GameState.canPour/pouring/legalMoves/isSolved` all delegate to it. Locked bottles are already rejected there (cheap, and the field exists now).
7. **Move counter.** `GameSession.moveCount` = number of moves currently applied, so Undo decreases it. Stars compare this with `minMoves`.
8. **Validation scope.** `validate()` checks: at least one bottle, capacity ≥ 1 and identical across bottles, no overfilled bottle, every color exactly `capacity` times. It does not check solvability (that's the solver's job).
9. **Per-user Xcode files untracked.** `xcuserdata/` removed from the index (files stay on disk) — user-approved.
10. **macOS input.** A click acts as a tap. Haptics only on iOS; the illegal-move shake animation runs on both platforms — user-approved.
11. **State encoding.** `StateKey` packs each bottle into a `UInt64` (6 bits per layer, ≤ 9 layers; lock id in the top byte) and sorts the codes → order-independent, includes `lockedBy`. Limits: capacity ≤ 9, color ids 0…61. Out-of-range states return `.unknown(.unsupportedState)`.
12. **Rules stay single-sourced in the solver.** The BFS generates moves through `Rules.pourAmount` / `GameState.pouring`; it doesn't re-implement pours on the packed form. Search tree stores only `(parent, move)` per node; paths are replayed from the start state, so canonical reordering never corrupts move indices.
13. **Pruning (all in `Solver.candidateMoves`).** (1) skip sources that are full + single-color; (2) skip pouring into an empty bottle when the whole source moves (canonical no-op); (3) only the first empty bottle is tried as an empty target. All three only remove moves whose result is canonically identical to the current state or to a sibling. Verified: solver optimum == naive unpruned BFS on 125 random small puzzles (test `matchesReferenceAndReplays`).
14. **Performance.** BFS was fast enough without A*: 8 colors / cap 4 / 2 empty solve in 9–42 ms in release (12 seeds, 4k–19k states). Debug-build test bound is 10 s.
15. **Hint API.** `Solver.hint(for:)` returns `HintResult` (`.move`, `.alreadySolved`, `.unsolvable`, `.unknown`) instead of `Move?`, so the UI can show "No solution from here — undo?".
16. **Dead-end ratio.** Exact when the whole reachable graph (with the same safe pruning) has ≤ 400k states: full BFS → reverse edges → mark states that can reach a win; ratio = unsolvable / all. Otherwise: 48 seeded random walks (length 1…2×minMoves) whose endpoints are solved with a 200k-state cap; ratio over decided samples (`deadEndMethod = .sampled`). Every starter-pack level was exact.
17. **Branching factor** = mean count of *all* legal moves (player's view, no pruning) over the states on the optimal path, excluding the final state.
18. **Score formula** (tunable): `minMoves + 1.5·log2(statesExplored) + 40·deadEndRatio + 0.5·branchingFactor`, rounded to 0.1. Dead-end weight raised 15 → 40 (user choice) so trap-heavy 1-empty levels rank as hard as they play.
19. **Generator seeds.** Attempt i of a config uses `seed + i`; a level's `meta.seed` alone (+ colors/capacity/empty) reproduces it. Own Fisher–Yates on SplitMix64 (stdlib `shuffle(using:)` isn't guaranteed stable across Swift versions). The min-moves filter runs before the full difficulty report (cheaper).
20. **Starter pack** (`levelgen --preset starter`): tiers 3c/cap3 ×2, 3c ×3, 4c ×7, 5c ×8, 6c ×6, 5c/1-empty ×2, 7c ×5, 6c/1-empty ×2, 8c ×5 (all cap 4 unless noted). Each tier has its own seed space (`seed + tier × 1e6`); the final pack is sorted globally by score (user choice), so color counts can interleave. Move ranges were tuned from measured distributions.
21. **JSON output.** Keys sorted, pretty-printed, layer arrays collapsed to one line for hand-curation. Extra meta fields (`statesExplored`, `deadEndRatio`, `branchingFactor`) are informational. Loader rejects unknown versions and duplicate ids, and validates every level.
22. **levelgen language mode.** The CLI target compiles in Swift 5 mode (a plain top-level script); the core library stays in Swift 6 strict mode.
23. **Project wiring.** `project.pbxproj` gained an `XCLocalSwiftPackageReference` to `Packages/BottleSortCore`, the `BottleSortCore` product dependency, and a `Levels` group whose `pack_01.json` is in the Resources phase (the app folder itself is a synchronized group, so new Swift files need no project edits).
24. **App architecture.** `LevelCatalog` (bundled pack), `ProgressModel` over a `ProgressStore` protocol (`UserDefaultsProgressStore`, key `progress.bestStars.v1`; a level unlocks when the previous one has ≥ 1 star), `GameViewModel` (`@Observable`, main actor) wrapping `GameSession`. Views hold no rules. Star thresholds live in core (`StarRating`).
25. **Background solving.** After every move the view model solves the new state in a detached task (1M states / 4 s cap). The result detects "stuck" (unsolvable) and is cached so Hint is instant; Hint falls back to a fresh background solve. Results for stale states are discarded.
26. **Stuck rule.** "Stuck — undo or restart?" shows when there are no legal moves, or the solver proves the position unsolvable. The player may keep moving while it's shown.
27. **Animation.** Pours animate with SwiftUI transitions (layers fade out of the source and slide in at the target), the selected bottle lifts, illegal moves shake (GeometryEffect) and fire `.sensoryFeedback(.impact)` (haptic on iPhone; no-op on most Macs). Win fires `.success`.
28. **Keyboard (Mac/iPad).** ⌘Z Undo, ⌘R Restart, ⇧⌘H Hint, Return = Next on the win card.
29. **Debug launch arguments** (DEBUG builds only): `-LPOpenLevel N` opens level N directly (ignores locks); `-LPDemoMoves K` plays the first K optimal moves through the normal tap path. Used for automated screenshots.
30. **One pour function.** `Rules.pour(from:to:) -> (source, target)?` computes the resulting bottles for every move kind (color run, or key → consume + unlock); `GameState.canPour/pouring/legalMoves` and the solver delegate to it. `Rules.pourAmount` remains as a derived helper (layers leaving the source; 1 for a key). Supersedes the "single legality check" part of #6.
31. **Key & lock rules** (Phase 5, spec wording): a key moves only when on top, always alone (`movableRunCount == 1`), and only into the bottle with `lockedBy == key`; that bottle unlocks and the key disappears (needs no free slot — a full locked bottle can be opened). Colors never go onto a key or into a locked bottle; locked bottles can't be poured from. A locked bottle or one containing a key is never "solved", so a win implies no keys and no locks.
32. **Key JSON / encoding.** Key layer = `{"key": n}`, bottle lock = `"lockedBy": n`; layer lists with keys are still collapsed onto one line. `StateKey` tokens: 0 empty, 1…47 colors 0…46, 48…63 keys 0…15 (lock byte = lockedBy + 1, limited to 0…15 too). Supersedes the limits in #11.
33. **Key validation.** Colors still exactly `capacity` each (keys don't count); each key id at most once as a layer (`duplicateKey`), at most one bottle per lock id (`duplicateLock`), and every lock has a key and vice versa (`lockWithoutKey`, `keyWithoutLock`). A key nested inside another locked bottle is allowed.
34. **Pruning with keys.** Rule 3 now only skips *unlocked* empty targets (a locked empty bottle is a key target, not interchangeable). Rule 2 likewise only applies to unlocked empty targets; a lone key "moves whole" but can't go into an unlocked bottle anyway. Rule 1 can't hit key bottles (`isSolved` is false). Verified against the naive BFS on 175 random lock levels (`matchesReferenceOnLockLevels`) plus a hand-made puzzle that needs the key (4 moves; wrong-key and buried-key variants are unsolvable).
35. **Lock generator** (`GeneratorConfig.locks`, `levelgen --locks N`, 0 ≤ N < colors). Same shuffled color layers as classic; then: (1) the first `N × capacity` layers fill N *full* locked bottles (keys 1…N); (2) the remaining `(colors − N) × capacity` colors plus the N keys are dealt in sequence into unlocked bottles of `capacity` layers, the last one partial — one bottle more than classic, its free space is where the keys "came from"; (3) a slot is "top" if it is the last of its bottle; the non-top slots are shuffled and the first N (in sequence order) become keys 1…N, colors fill the rest in shuffled order; (4) empties are appended. With `locks = 0` the RNG use and output are identical to before, so `pack_01.json` is unchanged. The "pre-solved bottle" rejection also covers a locked bottle that would be solved once opened.
36. **Hidden layers** (display only, solver ignores them). `LevelDefinition.hidden: Bool?` (JSON `"hidden"`, omitted when false). `GameSession(_:hidden:)` keeps a per-bottle `hiddenDepth` = bottom layers shown as "?": starts at `count − movableRunCount`, after each move `min(old, count − movableRunCount)`; stored with the undo history, so undo/restart restore it exactly. Query with `isHidden(bottle:layer:)`. (With the current rules the new value is never larger anyway, but the `min` makes permanence explicit.)
37. **Random levels.** `RandomLevel.generate(options, seed:, maxAttempts: 6, limits:, progress:)`: attempt i uses generator seed `seed + i`, no difficulty filter; rejected if a bottle is pre-sorted, or the solver says unsolvable/unknown. Default limits 1M states / 4 s per attempt. Result has the level (`id "random-<seed>"`, `hidden` in `.hidden` mode, meta seed = the attempt's seed) or nil after the cap, plus every attempt's outcome. Options clamp to colors 2…12, capacity 2…6, empty 0…4, locks 1…2 (and < colors; only used in `.locksAndKeys`). `progress(k, max)` fires before attempt k.
38. **Quick difficulty budget.** Random levels are scored with `DifficultyBudget.quick` (exact dead-end graph ≤ 50k states, else 12 samples × 20k states) so the button stays responsive (≤ ~2.5 s release on an M-series Mac for 12 colors/cap 6 or 10 colors + 2 locks). `levelgen` and the pack keep `DifficultyBudget.default` (unchanged numbers).
39. **Pour animation** (replaces the pour part of #27). Pure SwiftUI on both platforms. The view model applies the move first, then publishes a `PourEvent` (from, to, moved layer, amount, both bottles before the move, their hidden depths). The view only draws it and reports back with `finishPour(id)`. Taps during a pour are queued (up to 2) and replayed. Undo, restart and level changes cancel the pour with no animation. Win and stuck cards wait until the pour ends. A 3 s failsafe in the model ends a pour if the view never reports back.
40. **Bottle positions for the animation.** Each bottle reports its frame through an `Anchor<CGRect>` preference. A board overlay draws the source, the stream and the target while the two real bottles are hidden; the overlay re-reads the frames every frame.
41. **Driving the animation.** A `TimelineView` evaluates a pure `PourPose.at(t)` (1.1 s total) instead of chained `withAnimation` calls — easy to read and tune, and it can't drift.
42. **Liquid in a tilted bottle.** Drawn in the bottle's own space with the surface kept level: each layer keeps its area, and its boundaries are found by bisection on the bottle's rectangle (rounded corners ignored). The tilt angle is where the remaining liquid reaches the lip, kept between 55° and 86°. Surface sway is a small damped extra tilt. **Reduce Motion:** level change in place over 0.4 s, no flight, tilt or stream.
43. **Key & lock look.** Key/lock colors are a separate metallic list in `Palette` (`keyColors`, by `KeyID`), so they never read as a liquid. A key layer is a dark slot with a `key.fill` icon in its color; a locked bottle gets a `lock.fill` badge in the same color, dimmed contents and a tinted outline. The views only read `Layer` / `Bottle.lockedBy`; no rule is evaluated in the app.
44. **Key pour animation.** Same flight and tilt as a liquid pour, but no stream: the key leaves the source in one piece, falls (rotating, shrinking) into the lock at the target's center, then the lock scales up and fades (`unlock` = last quarter of the flow). The target gains no layer.
45. **Hidden layers in the app.** `BottleView` takes `hiddenLayers` = `GameSession.hiddenDepths[i]`; those bottom layers show as a grey "?" card. A reveal is a 3D flip (0.45 s, face swapped at 90°). While a pour animates, the source keeps its pre-move depth so the flip plays when the board bottle reappears. In the flying overlay the tilted Canvas draws the same glyphs at each band's center ("?" on hidden layers, the key icon on key layers), tilting with the bottle.
46. **Random levels in the app.** `RandomLevelMaker` (main-actor, observable) runs `RandomLevel.generate` in a detached task with a seed from the system RNG (1…999 999 999, so ids stay readable); the core stays deterministic for a seed. Progress hops back to the main actor; a generation counter drops stale results, and `cancel()` also cancels the task, which stops the core run (see #48). Settings are stored as plain `UserDefaults` keys (`random.mode`, `random.colors`, …) and clamped with `RandomLevelOptions.clamped`. Navigation uses a `Route` enum (`level`, `randomSettings`, `random(level, options)`). A random game gets `GameViewModel(randomLevel:options:)`: no `ProgressModel` (never recorded), title "Random · <mode>", and "New Random Level" on the win card regenerates with the same options in place.
47. **More DEBUG launch arguments** (extends #29): `-LPRandomSettings 1`, `-LPRandomGenerate 1`, `-LPRandomMode classic|locks|hidden`, `-LPRandomSeed S`; the saved settings can be overridden per run through the UserDefaults argument domain (`-random.colors 6`).
48. **Random levels are deterministic; cancellation is real** (amends #37 and #46). `RandomLevel.defaultLimits` is now 1M states with *no* timeout, so a seed gives the same level (or none) on every device; a wall-clock limit made the accept/`unknown` decision depend on device speed. Worst case is about 5 s per attempt (release, M-series Mac). Long runs are stopped by cancelling the task instead: the solver checks `Task.isCancelled` every 4096 states (`.unknown(.cancelled)`), and `generate` makes no further attempts once cancelled. The in-game analysis keeps its 4 s timeout (its result is never stored).
49. **Stricter validation** (extends #8 and #33). `validate()` also rejects what the solver can never handle — capacity above `StateKey.maxCapacity` (9, `invalidCapacity`), color ids above 46 (`colorOutOfRange`), key/lock ids outside 0…15 (`keyOutOfRange`) — and locks that can never open (`unopenableLock`): a key inside the bottle it unlocks, or behind a cycle of locks. A key nested in another locked bottle whose key *is* reachable is still allowed.
50. **Stale background work is cancelled** (app side of #48). The view model forwards cancellation into its detached solves (`withTaskCancellationHandler`), so a superseded per-move analysis or hint stops within 4096 states. Replay/Restart and Undo cancel a pending "New Random Level" (the finished level no longer replaces a board the player went back to), and so does leaving the game screen.
51. **Spec removed.** `BOTTLE_SORT_PROTOTYPE_SPEC.md` was deleted from the repo at the user's request; earlier entries still say "the spec" for the original requirements, which stay in git history.
52. **Multiple packs.** The JSON format gains optional `name` and `subtitle`. The app bundles every `Levels/pack_*.json` (the `Levels` group is now a synchronized folder, so adding a file needs no project edit) and lists them in file order. All packs are open; levels unlock in order inside each pack. The last viewed pack is remembered with `@AppStorage` (a per-device convenience).
53. **Harder packs by selection.** A `Tier` can set `pool = k`: generate `count × k` passing levels and keep the `count` with the highest score. Combined with higher color counts, size-5 bottles, locks, hidden layers and one-empty-bottle tiers, this lifts the average score from 35.7 (Starter) to 56.5 (Challenger), 68.6 (Expert) and 71.9 (Master, max 96.3). Locks & Keys (51.1) and Hidden Depths (46.4) are themed mid-difficulty packs; the score doesn't measure hidden information. Measured limits: one empty bottle makes 6+ colors at size 4 unsolvable in 20/20 samples, so one-empty tiers use 5 colors, or 6 colors at size 5.
54. **Presets.** `levelgen --preset starter|challenger|expert|locks|hidden|master|all`. Each preset has its own base seed (1, 2000, …, 6000) and id prefix (`p1`…`p6`), so ids are unique across packs and regeneration is reproducible. `starter` reproduces the original `pack_01` levels exactly.
55. **Shipped-pack test budget.** `swift test` (debug build) solves only levels whose recorded search was ≤ 8 000 states (81 of 180), keeping the suite at ~20 s; every level is re-solved against its `minMoves` by `levelgen --report` in release.

56. **Roadmap direction (user choices).** Product name **Pourfect** with the full Potion Lab theme; code and module names stay neutral. Main path = star-gated chapters, one new mechanic each (MECHANICS.md §3); the current hard packs become an optional Challenges area.
57. **Roadmap order.** Polish → theme & chapters → daily puzzle → mechanics architecture → mechanics (C1, C2+C4, D1, D2, F1+F2, E1, A3) → challenge modes → orders & story → release. Not planned: A2 corks, B2 scrying glass, C3 cauldron capacity, C5 density, D3 conveyor, D4 evaporation, E2/E3, F3 teleports, items.
58. **Assets are generated in code.** Sounds are synthesized with AVAudioEngine; art is SwiftUI shapes, gradients and Canvas particles. Real asset files can replace them later behind the same hooks.
59. **No Game Center, iCloud or notifications.** The user has a developer account but doesn't want them; the daily puzzle works fully offline. TestFlight may come later.
60. **English only**, but all UI text goes through a String catalog so languages can be added cheaply.
61. **Design docs are tracked.** `FUTURE_FEATURES.md` and `MECHANICS.md` are committed (they still mention the removed prototype spec by name).
62. **Daily seed = UTC calendar date** so every player gets the same puzzle on the same day regardless of time zone (user-confirmed).
63. **Chapter gate:** a chapter unlocks when the previous chapter has at least half of its possible stars (user-confirmed).
64. **Hints in murky levels** stay unlimited on the main path (user-confirmed).
65. **Mixing-cauldron levels** are built backwards from a solved board, then verified by the solver (user-confirmed exception to "no backward scrambling").
66. **Bundle id `dev.qbi.pourfect`** (from the user's domain qbi.dev), applied now. Saved progress from the old placeholder id doesn't carry over.
67. **Assets:** sounds, vector art, runes and the app icon are generated in code/SVG; raster art (painted backgrounds, portraits) is listed for the user to supply later as an upgrade.
68. **Roadmap workflow:** each R-step ends with a Mac-app test checklist for the user; it's pushed to GitHub only after the user's OK.
69. **Flask completion lives in the core.** `Rules.isCompleted` = solved and not empty; `Rules.completedBottles(before:after:)` lists bottles that newly became complete. The view model computes it when the move is applied, keeps it in the `PourEvent`, and reports it when the animation lands (`finishPour`), so the cork/sound/haptic line up with the visuals. Undo/restart drop it with the pour.
70. **Feedback events.** `GameViewModel.feedback` is a short ordered log of `Feedback(id, event)` (`select`, `illegal`, `pour`, `flaskCompleted`, `levelWon`) rather than a single "last event", so events published in one update (a landing pour followed by a queued tap) are never coalesced away. Views observe `feedback.last?.id` and read `feedback(after:)`. Per-bottle `completions` counters (like `shakes`) drive visuals.
71. **Settings value and store in the core.** `GameSettings`, `ReduceMotionPreference` and `SettingsStore` / `UserDefaultsSettingsStore` are Foundation-only and live in BottleSortCore so persistence is covered by `swift test` (the app has no test target). The observable `AppSettings` wrapper and the environment values (`colorRunesEnabled`, `effectiveReduceMotion`) are in the app. Each setting is its own key, so one bad value falls back alone.
72. **Sound design.** All sounds are synthesized once at launch (deterministic seeds) into mono 44.1 kHz buffers, peaks 0.13–0.24 so they stay soft. Eight player nodes round-robin with `.interrupts`. The engine starts lazily, is rebuilt/restarted on the next sound after a configuration change or interruption, backs off 2 s after a failed start, and never starts without an output device. iOS session `.ambient` + mix with others.
73. **Haptics are imperative** (`UIImpactFeedbackGenerator` / `UINotificationFeedbackGenerator`) rather than `.sensoryFeedback`, because they are driven by the event log and gated by the haptics setting. The Mac has none, so the Haptics toggle is hidden there.
74. **Cork follows the state, the drop follows the event.** A cork is drawn whenever `Rules.isCompleted(bottle)` holds, so undo/redo/restart are always right; it pops off (removal transition) when the flask stops being complete. The drop-with-bounce and the sparkle burst (16 deterministic sparkles in the potion's color, 0.6 s, Canvas + TimelineView) play when `completions[i]` changes, i.e. when the pour lands with the cork-pop sound. A completed source that is poured from loses its cork at the start of the pour animation (`PourPose.corkOff`). With reduce motion: no drop, no bounce, no sparkles.
75. **Glass look is shared.** `GlassSheen` (soft left sheen + faint right line, over the liquid) and `potionGlow` (a blurred, faded copy of the liquid behind it, so each layer glows in its own color without tinting it) are applied identically in `BottleView` and the pour animation (`FlaskDecor.swift`).
76. **Runes.** `Rune` (Model/Runes.swift) is the single definition: 12 stroke paths indexed by color id (triangle, wave, star, chevron, crescent, bolt, diamond, heart, square, cross, hexagon, ring), drawn white over a thin dark outline at half a layer's height. One rune per layer, also inside merged runs; never on "?" or key layers. In `TiltedLiquid` runes don't affect band merging: they are drawn per original segment after the bands, tilt with the bottle and shrink with a draining/filling layer. `UserDefaultsSettingsStore` also reads string booleans, so `-settings.colorRunes 1` works as a launch argument.
77. **Cork drop runs outside the pour's animation.** The pour lands inside `withAnimation`, and that animation also eased the jump to the first keyframe: the cork started at its seat, and the leftover of that eased jump pushed it about half a flask width into the liquid while the keyframes were already back at rest (measured from screen captures; the keyframe values themselves never go below the seat, and a `.transaction` modifier on the animator did not stop it). `BottleView` now drives the animator from its own `corkDrops` counter, bumped in a transaction with animations disabled when `completions` changes. The keyframes are eased linear segments (a cubic spline through the seat dips a little below it).
78. **Reduce Motion never replays a drop.** `corkDrops` only follows `completions` while motion is on, so switching Reduce Motion in Settings doesn't change the animator's trigger (before, the trigger flipped between 0 and `completions` and every cork dropped again).
79. **Sounds are synthesized off the main actor.** `SoundSynthesis` (nonisolated) builds all samples in a detached task when `SoundEngine.shared` is first touched (now at app launch); the main actor only copies them into `AVAudioPCMBuffer`s. In the unoptimized Debug build synthesis takes ~0.75 s, which used to block opening the first level. Sounds requested before it finishes are skipped; the output is byte-identical to before.
80. **Delayed feedback is cancellable.** `SoundEngine` keeps its delayed sounds as tasks and `FeedbackPlayer` its delayed haptics; `FeedbackPlayer.cancelPending()` drops them. It runs when a pour is cancelled mid-animation (`GameViewModel.cancelledPours` goes up in Undo / Restart / level load), when the game screen disappears, and when Sound is switched off (`stopAll()` also cancels). Sound already playing is left to finish.
81. **Pourfect name, neutral code.** `INFOPLIST_KEY_CFBundleDisplayName = Pourfect` (home screen, Finder) and `InfoPlist.xcstrings` localizes `CFBundleName` to Pourfect, so the Mac menu bar (About/Hide/Quit Pourfect) and LaunchServices show the new name while `PRODUCT_NAME`, the target, the module and the executable stay `LiquidPour`. `WindowGroup("Pourfect")` and the level list's navigation title use it too.
82. **Wording.** Flasks, recipes, chapters; Random Level → **Random Brew** (modes Classic / Rune Seals / Murky Layers, "Brew" button, "New Random Brew", "Next Recipe", win card "Brewed!"). Pack names and subtitles still come from the level JSON and are not localized (they are data).
83. **String catalog.** `Localizable.xcstrings` (English, source language) holds every UI string; non-`Text` strings use `String(localized:)`. Counts with plural forms (stars, moves, flasks, murky layers, tries) use catalog plural variations/substitutions. The catalog was generated from the build's `.stringsdata` (what Xcode's IDE does on build), so it matches the code exactly.
84. **Workbench background.** `WorkbenchBackground` aspect-fills the painted workbench (landscape art when width ≥ 0.9 × height, else portrait), with a 1.5 pt blur, a 28 % black dim, a darker band across the middle and a vignette. The game screen runs in a dark color scheme (`.environment(\.colorScheme, .dark)`, and a dark navigation bar on iOS) so the glass outlines (`Color.primary`) and materials stay light on the dark scene; HUD and controls sit on ultra-thin material capsules, the result card on thick material. The level list uses `.menu`: heavily blurred art washed with the system background at 78 %, so it works in light and dark mode.
85. **Glass on a painted background.** Resting flasks get a smoky backing (`BottleView.glassBacking`, black 30 %) so empty glass reads on the art. The pour animation used an opaque `.background` fill behind the flying flask (to hide flasks it passes); on the painting that showed as a solid slab, so the target now uses the same smoky backing as at rest and the lifted source fades to a frosted `regularMaterial` backing as it rises (`opaque = min(1, rise × 1.6)`).
86. **Flask rim.** A thin glass lip (`FlaskRim`, 1.1 × the flask width, ~0.1 w tall) is drawn over the top edge in both `BottleView` and the pour animation. It's decoration only: the bottle shape, liquid clipping, tilt maths and cork position are unchanged, so fills stay pixel-identical. The rim follows the outline color (selection, hint, seal).
87. **Potion names** live next to `Palette.colors` (`potionNames`, same index) and are used for VoiceOver (`Layer.spokenName`, `Bottle.spokenContents(hiddenLayers:)`); hidden layers are spoken only as a count of murky layers, so VoiceOver never leaks them.
88. **Pack metadata.** `LevelPack` gains optional `kind` (`chapter` | `challenge`), `chapter` (1-based), `location` and `introduces: [Mechanic]`; v1 files without them still load (format version stays 1). `Mechanic` is a string wrapper (`basic`, `sealed`, `murky`, …) so files naming mechanics this build doesn't know still load. A `kind: chapter` pack without a chapter number ≥ 1 is rejected (`missingChapterNumber`). `name` stays the display name (for chapters it equals `location`); the app decides the "Chapter N · …" wording.
89. **Chapter gate in the core.** `ChapterGate.isChapterUnlocked(n, previous:)` = `n == 1 || stars × 2 ≥ maxStars` (maxStars = 3 × recipes, exactly half counts, an empty previous chapter doesn't block). `unlockedChapters(_:)` applies it in order and also needs every earlier chapter open, so stars left in a chapter that is closed again can't skip ahead. `ChapterProgress.starsToOpenNext` = ⌈max/2⌉ − stars for the UI. Recipes inside a chapter: the first is open, each further one when the previous is cleared (`isRecipeUnlocked`). Saved stars are clamped to 0…3. `ChapterOutline.plan` lists all ten planned chapters (location + mechanics) so the app can draw "coming soon" entries.
90. **New file set.** `Levels/` now holds `chapter_01.json` (= old `pack_01`, ids `p1_…`), `chapter_02.json` (Rune Vault, `c2_…`), `chapter_03.json` (Misty Marsh, `c3_…`) and `challenge_challenger|expert|master.json` (= `pack_02/03/06`, ids unchanged). `pack_04` (Locks & Keys) and `pack_05` (Hidden Depths) are deleted; their `p4_`/`p5_` ids are not reused. The renamed files were moved with `git mv`; regenerating them only added metadata (levels are byte-identical). The app's `LevelCatalog` still filters `pack_*` and has to switch to the new names.
91. **Locks must matter.** Winning always needs every key, so "the key is used" is trivially true. `LockImpact.lockMatters` instead compares with the same level without that lock (flask unlocked from the start, key layer removed): the lock matters if that level is unsolvable or the locked level needs more than one extra move (the key pour). Each lock is checked on its own; an undecided solve counts as "doesn't matter". `GeneratorConfig.requireLocksMatter` (default off, so older presets reproduce) applies it after the minMoves filter; `levelgen --report` counts a chapter lock that doesn't matter as a problem. A key lying on top of a flask that just needs emptying fails the check, which is why the chapter 2 tutorial is generated (key under a short run) rather than hand-made.
92. **Chapter presets.** Tiers can set a score window (overrides `--min/max-score`), `locksMatter`, `keepEasiest` (tutorial: easiest of a small pool) and a `section`; a pack is sorted by score inside each section and sections follow each other. Chapter 2 (seed 7000): tutorial (3 colors, size 3, 1 seal, 6 moves), then one seal with 3→6 colors and one-empty levels, then 8 recipes with two seals. Chapter 3 (seed 8000): tutorial (3 colors, size 3, 5 moves), 21 murky recipes with 4→6 colors and one-empty levels, then 8 murky recipes with one seal (6–7 colors). Measured scores: Ch. 2 tutorial 15, then 24 → 53 (mean 38.8); Ch. 3 tutorial 15, then 28 → 54 (mean 38.2); Ch. 1 ends at 52 and Challenger averages 56.5. The score ignores hidden information, so murky recipes play harder than their number. Full regeneration takes about 90 s.
93. **`levelgen --report DIR`.** Reports every `*.json` in a folder, prints min/mean/max and the score curve in file order, and exits with status 2 on any problem (minMoves mismatch, or a chapter lock that doesn't matter). The shipped-file test budget (#55) is unchanged: `swift test` solves only levels with a recorded search ≤ 8 000 states and checks their locks; the release report re-solves all 180 levels.
94. **Catalog from metadata.** `LevelCatalog` loads `chapter_*`, `challenge_*` and legacy `pack_*` files and splits them into `chapters` (by chapter number) and `challenges` (by file name) from the pack metadata (this resolves the open point in #90). A file without metadata falls back to its name: `chapter_NN` is chapter NN, anything else a challenge. A second file claiming the same chapter is skipped and reported. `catalog.packs` = chapters then challenges, which is the numbering `-LPOpenPack` uses (1–3 chapters, 4–6 Challenger/Expert/Master).
95. **Gate in the app = core rule.** `ProgressModel.unlockedChapters` feeds `progress(of:)` (clamped stars per recipe id) into `ChapterGate.unlockedChapters`; recipes use `ChapterGate.isRecipeUnlocked`. Stars saved for ids that no longer ship (`p4_`, `p5_`) are never asked for, so they're ignored without a migration. `-LPUnlockAll` opens chapters and recipes alike.
96. **Chapter map is the home screen.** `chapter_map` is drawn at its aspect ratio in a vertical scroll view; the ten buttons are placed by hand on the path's clearings as fractions of the image (`ChapterArt.mapSpots`), so they scale with any width. The map opens scrolled to the current chapter (`defaultScrollAnchor` at its spot — `ScrollViewReader.scrollTo` on `.position`ed markers was unreliable). Wide windows (≥ 760 pt) show the map as a framed column beside a panel (title, total stars, Continue, Challenges) over a blurred copy of the map; narrow ones fill the width with a Continue / Challenges bar as a safe-area inset. Closed markers use `allowsHitTesting(false)` rather than `.disabled`, which faded them on the Mac.
97. **Challenges area** holds Random Brew and the three challenge books; the old level-select screen (`LevelSelectView`) is gone. Chapter and challenge books share `PackView` (painted header + recipe grid; chapters show what their stars open).
98. **Tips per mechanic.** `TutorialTopic` (`basic`, `sealed`, `murky`) is derived from what a recipe actually contains (seals, murky flag) plus the pack's `introduces` for its first recipe; a recipe with nothing special teaches `basic`. Unseen topics show once as an overlay (steps drawn with `BottleView`, so they look exactly like the game) and are marked seen on "Got it"; the "?" in the HUD (⌘/) shows the current recipe's topics any time. The seen-state sits behind `TutorialStore` (UserDefaults, one key per topic). Random Brew recipes show tips too.
99. **Map art is not tinted per state.** Open chapters show their vignette in color with a white ring (gold when all stars are earned, orange glow for the current chapter); locked ones are desaturated with a lock and "N more ★ needed"; planned ones show an hourglass and "Coming soon". Location names come from the data (pack name or `ChapterOutline.plan`) and are not localized.
100. **A cleared recipe stays open.** `ChapterGate.isRecipeUnlocked(at:in:isCleared:)` opens a recipe when the previous one is cleared *or* the recipe itself is cleared. Stars earned out of order (debug launch args, or a future reorder of a chapter) are never hidden behind a lock while they still count toward the chapter total.
101. **Locked recipe cells are not `.disabled`.** On the Mac a disabled plain button greys its label out on top of the cell's own locked look, which made locks and numbers unreadable in light mode. Locked cells draw a dimmed primary on a denser material and ignore taps (`allowsHitTesting`), and the action is guarded too.
102. **Random Brew is themed like the other menus**: painted workbench backdrop behind the grouped form (hidden form background) and the Settings button in the toolbar.
103. **Lock strength stays at "+1 move" for now.** A review probe found that no shipped lock makes its recipe unsolvable when removed, and 26 of the 38 locks in chapters 2–3 add exactly one move beyond the key pour, so the #91 threshold is met at its minimum. Raising it (≥ 2 extra moves, or unsolvable without the lock) means regenerating Rune Vault and Misty Marsh; that is a design call left open (see PLAN R2 notes), not a bug.
104. **Flask modifiers.** `Bottle.modifiers: [BottleModifier]` is a set (deduplicated, sorted in a canonical order on every write), stored compactly: no modifier and a lone seal need no array, so classic and sealed bottles copy as cheaply as before (an array-backed first version cost ~20 % solver time). `lockedBy` is a computed accessor for the `.sealed` modifier (get/set), so the app compiles unchanged. All R5 cases are defined now (`essence`, `narrowNeck`, `funnel`, `tap`, `frozen(layer:turns:)`, `bubbling(every:phase:)`, `cauldron([Recipe])`); only `.sealed` is implemented. Unimplemented modifiers, links and goals are rejected by `validate()` (`unsupportedMechanic`) and by the solver (`.unsupportedState`) instead of silently playing as classic flasks. A bottle with two seals is a validation error until multi-rune seals exist.
105. **One modifier pipeline.** `Rules.apply(_:as:to:)` is a single switch over (modifier, side) that may veto a pour or change a `PourPlan` (`limit`, `opensSeal`; R5 adds fields such as pour-from-bottom). `Rules.plan(from:to:)` runs source modifiers, then target modifiers, then the base rule, and builds no bottles, so legality checks (solver candidates, `canPour`) stay cheap; `transfer` applies the plan. `Rules.pour(from:to:)` stays public as the two-bottle view. The seal migration is checked against a verbatim copy of the old rules on up to 720 lock states (generator candidates and random walks).
106. **Frozen layers are a modifier with a layer index**, `.frozen(layer: i, turns: n)` (0 = bottom), not a `Layer` flag. A frozen layer and everything below it can't move, so the index stays valid while it is frozen (a tap or bubbling flask must respect that in R5). `Layer` stays a plain enum, so runs, equality and the 6-bit layer tokens are unchanged. The bubbling phase also lives in its modifier.
107. **Links and goal live on `GameState`** (`links: [Link]`, `goal: Goal`), referencing bottles by index, in one shared box that is nil for the default, so a classic state copies one more nil reference. Switch → gate is a link whose gate state is derived from the switch's content (no stored state). `GameState.permuted(by:)` / `shufflingBottles` renumber links and goal targets with their bottles (the classic shuffle is unchanged).
108. **`moveCount` is optional.** It is stored (and incremented by `resolve`) only when a rule needs it (a timed mechanic or the rescue goal); classic states keep nil, so states reached at different depths still share keys.
109. **`Rules.resolve(_:afterAction:)`** is the turn: action → immediate effects (unseal) → move counter → timed effects (empty hook, fixed order corks → thaw → bubbling → evaporation → conveyor) → immediate effects again if a timed effect changed anything → goal check. It returns a `Turn` (state + `isWon`); `GameState.pouring`, the solver and the state graph use it. Unsealing moved from the pour itself to step 2: the pour reports the key it delivered and `resolve` opens the seal. `GameState.isSolved` = `Rules.isMet(goal, by:)`.
110. **StateKey v2.** Classic and sealed states (no links, standard goal, no counter, at most a seal per bottle) produce exactly the v1 words (checked against the old packing and by golden fingerprints of every shipped level). Anything else: bottle groups (v1 word with an extension flag, then a count and modifier words) sorted lexicographically, then a marked global section with links, goal and move counter. Link endpoints and goal targets are written as the canonical rank of their bottle; bottles with identical groups are tied, and the rank assignment of tied bottles that gives the smallest global section is chosen, which makes the key canonical (permutation-invariant) and injective up to isomorphism. Past 720 tie assignments the bottles' own order breaks ties (still correct, less deduplication). Release timing for an 8-color state: v1 0.16 µs per key, v2 with modifiers 1.0 µs, v2 with a link between tied bottles 2.1 µs; the classic solver is unchanged (bench `--colors 8`: mean 0.029 s before and after; `--colors 7 --locks 2`: 0.18 s before, 0.16–0.17 s after).
111. **The solver prunes only classic states.** The three pruning rules assume plain or sealed flasks of one capacity without links; any other state gets every legal move until its mechanic adds safe pruning. Cross-checked against the naive BFS with a move counter forcing the unpruned path.
112. **Level format v2.** Bottles gain `modifiers` (everything but the first seal, which stays `lockedBy`), levels gain `links` and `goal`, each written as an object with a `"type"`. `LevelLoader.encode` writes `version` = `requiredVersion` (2 only if a level uses one of these), so all shipped files re-encode byte for byte and `levelgen --preset all` regenerates them identically. `LevelLoader.decode` checks structure only (round-trips of not-yet-playable levels); `load` also validates. A version-1 file that uses v2 fields is rejected (`needsVersion2`); version 3+ is unsupported.
113. **`MechanicImpact`** generalizes the must-matter check: `instances(in:)` lists every seal, other modifier, link and non-standard goal; `matters` re-solves without one and requires the level to become unsolvable or to lose more than the instance's inherent cost (1 for a seal's key pour, 0 otherwise). `LockImpact` is now its seal case with identical results; `levelgen --report` checks every instance of a chapter level (one warning per instance).
